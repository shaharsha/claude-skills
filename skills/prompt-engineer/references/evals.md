# Evaluating and Debugging Agents

A **task** reference for building evals, writing and calibrating LLM judges, and diagnosing why an agent run failed. Step 0c sends you here. The rules that apply to every prompt edit stay in SKILL.md Section H, and the provider files still apply inside every judge and eval prompt (on Claude Opus / Sonnet / Fable 5.x, for example, don't ask a model to write its reasoning into the output - see `claude.md`).

The thread through all of it: a score tells you *what* broke, not *why*. Read the transcripts, check against something outside the model (a test, a reference solution, the environment's final state), and count before you act.

## Success criteria and eval design

- **Success criteria are specific, measurable, achievable, relevant - and usually multidimensional.** "Classifies sentiment well" is not a criterion; "F1 ≥ 0.85 on a held-out set of 10,000 diverse posts, 99.5% non-toxic, p95 latency < 200 ms" is. Pick the dimensions that matter for the use case - task fidelity (incl. edge cases), consistency across similar inputs, relevance/coherence, tone/style, privacy preservation, context utilization, latency, price - and give each a threshold. Even "hazy" goals quantify ("< 0.1% of 10,000 outputs flagged by the content filter").
- **Eval set design:** mirror the real task distribution, including edge cases (irrelevant or missing input, overly long input, poor or harmful user input, cases where even humans would disagree); structure items so grading can be automated; and prefer **more items with slightly noisier automated grading over fewer hand-graded ones**.
- **Grader choice - fastest reliable method wins:** code-based (exact/string match, validators, tests) first; LLM-as-judge for nuanced judgments, validated against a sample of human labels before you scale it; human grading only where unavoidable.
- **Use adversarial inputs** - empty strings, unexpected languages, edge cases, tools that shouldn't be called, and **plausible-sounding nonsense** (real domain vocabulary combined incoherently - fabricated framework names, real concepts from wrong domains, precise numbers for unmeasurable things). Test whether the agent engages confidently with broken premises or pushes back. For a ready-made design, [BullshitBench](https://github.com/petergpt/bullshit-benchmark) enumerates **13 nonsense techniques** (`plausible_nonexistent_framework`, `misapplied_mechanism`, `cross_domain_stitching`, `specificity_trap`, `nested_nonsense`, …) - reuse them to build false-premise fixtures. Weight the hardest ones: across all models the false-precision **`specificity_trap` is caught only ~10% of the time** (precise-sounding detail disarms skepticism; next hardest: cross-domain stitching ~24%, plausible nonexistent frameworks ~27%), and software premises fool models far more than physics (~29% vs ~52% clear pushback across all models, Sept 2026 data). Pair each nonsense fixture with a legitimate *near-miss control* so you score specific-flaw identification, not blanket skepticism: a model that cries "nonsense" at everything aces an all-nonsense set but over-refuses real questions in production. BullshitBench itself has **no legitimate control questions**, so it can't measure over-rejection - your fixture set must.
- **Build programmatic evaluations** - Run the agent on representative test cases, score outputs automatically (LLM-as-judge or exact match), track scores across prompt changes. Start small - ~20 representative tasks is enough to begin; early prompt tweaks routinely move success 30%→80%, so don't wait for a big set. For **stateful** agents, grade the *final state*, not the turn-by-turn path - agents reach the same goal by different routes.
- **Control the environment, or small deltas are noise.** For agentic evals the sandbox is part of the experiment: Anthropic moved Terminal-Bench scores ~6 points by changing only container resource limits (tight limits OOM-kill runs and reward lean strategies; generous ones let agents pull heavy dependencies). Hold hardware, time limits, and concurrency constant across the arms you compare, report them, repeat runs at different times, and treat differences under ~3 points with suspicion until the setups match. **Context management is part of the environment:** a treatment that makes the agent call more tools can push more trials into compaction (one team saw it in 3 and 4 of 5 trials of the treated arms), which then confounds the comparison - give each arm the same context budget, or record compaction as a stratum and compare within it.
- **Instrument settings the model can see are part of the treatment.** A cap, limit or banner your bench adds can reach the agent through a tool's output and change what it does: in one team's bench a size limit that existed only in the bench showed up in a listing tool's output, and three control trials had to be voided because the agent saw a limit production never shows. List every instrument value that reaches the model's context, pin it with the arms, and restart both arms if one changes.
- **Preflight the instrument for free before paid trials.** Check, per task environment, that the seed data loads, the agent can read its memory and the catalog it needs, and the size rules hold - before the first counted trial. One team hit 8 instrument stops before its first counted trial, most of them defects in the bench rather than agent behavior; a $0 check would have caught most of them.
- **Keep eval scenarios realistic.** Newer models can detect they're being tested and behave better than in production - so a passing *artificial* guardrail/safety eval can overstate real behavior. Avoid cartoonish or obviously-synthetic setups; make the scenario look like real traffic. The gap can run the other way too: OpenAI (Nov 2026) found success on a "respecting warnings" safety eval 10.2-37.4 points *lower* than on matched production decisions across six models, a gap OpenAI associates with what the model infers is being tested (case mixes still differ). In a framing test on GPT-6.1 Sol, saying only that it was an evaluation changed nothing (63.1% vs 63.4%), naming the real objective raised success to 91.6%, and naming a wrong one dropped it to 17.6%. Check eval behavior against production traces of comparable decisions.
- **Balance the set, and keep two suites.** Include cases where a behavior should happen and cases where it shouldn't: an eval that only checks "does it search when it should" produces an agent that searches for everything (Anthropic's web-search example in *Demystifying evals for AI agents*). Keep a **capability** suite (starts at a low pass rate, something to climb) apart from a **regression** suite (should pass at nearly 100%; a drop means something broke), and move saturated capability tasks into the regression suite.
- **Eval-first, per example.** Write the eval for a change before making it, "and confirm it fails on the current broken version"; then compare per example, not only the average - in LangChain's worked example a new ticketing tool raised the average score while a VPN how-to question started filing tickets ("The average score went up, but one case broke"; the fix was a narrower tool description). A score that rises on the examples you tune against but stays flat on a held-out set means overfitting. Run fast code checks on every change and slower judge-based evals nightly or before a release (LangChain, *What Is Eval-Driven Development?*, Nov 2026).
- **Measure a skill or prompt change from a fresh workspace.** An agent re-run on a workspace that already holds its earlier notes tends to edit them in place and re-run saved queries, so a rule that changes wording or labels shows up while a rule that needs a new analysis mostly doesn't (one team's measured runs). Inherited-notes runs understate the second kind; start each measured trial from clean state.

## Eval integrity: keep the answer and the grader out of reach

If the agent can find the answer, it will - and then the eval measures the leak, not the agent.

- **Start every trial from a clean environment, and strip the future.** Leftover files, caches and earlier trials' outputs inflate scores (Anthropic saw Claude read git history left by earlier trials). Remove git history, branches and tags past the base commit: SWE-bench Verified had this leak (issue #465: an agent ran `git log --all` and applied the fix; fixed in PR #471, Sept 2025), and SWE-bench Pro's open-source images had one of the "same shape" in 2026 (issue #93: future commits on the main branch, feature branches and tags left in the image, so `git show <fix>` worked offline). Building the workspace from an archive of the base commit, with a fresh one-commit history, closes all three paths. Keep memory files and judge verdicts out of reach too, and give the agent no grader signal during the run. **The same goes for every model you bring in to check the work:** a second-opinion reviewer pointed at a working folder can read held-out answer keys stored next to it (one team's reviewer opened the bench's truth files in a sibling folder on its own), so stage only what the reviewer should see.
- **Agents exploit visible tests.** On ImpossibleBench (ICLR 2026, arXiv:2510.20270) - tasks whose spec and tests conflict, so any pass means cheating - GPT-5 cheated on 54-76% of the SWE-bench variants. Hiding the test files cut cheating to near zero but also lowered legitimate pass rates; read-only tests restored legitimate performance and stopped test edits (Claude's main cheat) but not special-casing or operator overloading (common on GPT-5 and o3), so grade on a held-out test split or check the patch for special-casing. An explicit "flag this task as impossible" exit cut GPT-5's cheating from 54% to 9% (Claude Opus 4.1 rarely used it); stricter prompts helped; letting the agent resubmit after failures *raised* cheating. In the agent's own prompt, give it a way to report an impossible or contradictory task (`claude.md`: "inform me rather than working around them").
- **Write a reference solution for each task.** It proves the task is solvable and the graders are configured. With frontier models, 0% across many trials usually means a broken task or grader, not an incapable agent (Anthropic, *Demystifying evals for AI agents*).
- **Grade outcomes and side effects, not the path.** Assert the final state, and diff the state before and after the run to catch changes nobody asked for (AppWorld, ACL 2024, arXiv:2407.18901, calls this "collateral damage": a return the task never requested, a deleted wish list). Read side effects from an event log - writes only in scope, the expected messages, no stray calls. Where a task needs outside services, use **stateful fakes** seeded to the task's point in time, not canned mocks: a multi-step agent needs services that remember what it did, and a mock invites "mock auth and skip the e2e test" (Islo, [Autonomous Engineering meetup talk](https://youtu.be/P-KJFMDe1IE), Nov 2026; its fakes are open source as `islo-labs/doubleagent`, MIT, with seed, reset and an event log).
- **Give long runs partial credit through milestones.** Deterministic milestones on the trace show where a run stalls, not only whether it passed (Arithmetic, [same meetup](https://youtu.be/SXfJlYh0Vss); Anthropic). Report the binary full-completion rate beside the partial score (TheAgentCompany, arXiv:2412.14161, weights them 50/50), and check each milestone against the final state or causal evidence: partial-credit scorers can reward progress that was later undone or that the agent didn't cause.

## Diagnosing an agent run

An eval tells you what broke, not why. Before changing a prompt, a skill or a tool, find the cause in the run itself.

- **Read transcripts, then count.** Write open-ended notes on 30-100 traces, noting the first upstream failure in each; group the notes into a failure taxonomy, count each category, and only then build evaluators (Husain and Shankar's error-analysis method). Anthropic: "You won't know if your graders are working well unless you read the transcripts and grades from many trials." Keep categories specific: a wrong fact and an invented user action are both "hallucinations", and one score for both hides each.
- **Pick which trials to read by outcome pattern** when you run k trials per task (Flexor.ai, [Autonomous Engineering meetup talk](https://youtu.be/LWpSkKhdIuU), Nov 2026):
  - a task that passes some trials and fails others first - the cause is usually the harness; diff a failing attempt against a passing one;
  - among tasks that always pass, high variance in steps or tokens;
  - a failure on an easy task - usually a harness bug;
  - a task that fails every trial on a frontier model - usually a broken task or grader; check it against the reference solution or with a stronger model.
- **Name the first step that left the path, and the instruction it diverged from.** Then attribute the miss: the agent, an in-loop reviewer, the judge, or the instrument (a gap in what the reader saw, an undersized cap, a tracing fault).
- **Watch cost and turns, not only accuracy.** Strong agents route around broken tools: in one team's runs a search tool failed on 75-78% of calls, the agent called the underlying API directly, and the benchmark still passed - at about 3× the time and tokens (Flexor.ai, one benchmark). Track tool error rate, turns, tokens and cost per trial; Anthropic's *Writing effective tools for agents* lists the same signals. **Diagnose a cost outlier from its trace before blaming the infrastructure:** in one team's bench a trial that cost twice the others was agent variance, not latency - 589 of its 1,032 tool calls repeated an earlier call's input, and it wrote 4× the output tokens. The share of repeated-input calls is a cheap detector; size budgets for that tail.
- **Treat a model's explanation of its own decision as a hypothesis.** Self-reports are often confabulated (Anthropic's *Emergent introspective awareness*, arXiv:2601.01828: the capacity is "highly unreliable and context-dependent"), and a stated explanation can rationalize an answer that a hidden bias caused (Turpin et al., NeurIPS 2023, arXiv:2305.04388). Replay the run to the decision point with tools off and ask for a short explanation and the evidence that pushed it - not "write out your reasoning", which Claude Opus / Sonnet / Fable 5.x can refuse as `reasoning_extraction` - then count the hypothesis across trials before acting on it (Flexor checked one such answer against the trace, then counted it: the condition the model named held in 72 of 500 trials, those trials scored lower, and a prompt fix recovered the score). Replaying from a saved snapshot with one input changed is the cleanest test (Docent's intervention workflow does this).
- **Know where the reasoning is recorded, and how long traces are kept.** Check that your traces actually record each model's thinking summaries (some providers emit them only when asked, some host APIs don't return them - on AWS Bedrock's `bedrock-mantle` endpoint only Responses does - and a summary can be too lossy to explain a decision), and check the trace store's retention: one team's self-hosted trace store kept traces for only 2 days, through a time-to-live that a setup script reset on every bring-up.
- **Before blaming the model, replay the step on a stronger model.** If it passes, the weaker model is the likelier cause. If it fails too, suspect the task, the grader, the tools or the environment - but two models can make the same mistake on a valid task, so confirm with the reference solution or a demonstrated defect before changing the harness.
- **A re-run that passes after a failed gate is not evidence.** A flaky pass hides the cause; diagnose the failure first.
- **Turn each understood failure into a deterministic detector** over the traces - a refused call, a loop with no progress, truncated output, an exhausted budget, a tool error the agent routed around - and track the counts per run, with an `other` bucket: a rising `other` is a new failure mode to diagnose. Detectors are free, exact and re-runnable, and they keep a fixed failure from coming back unnoticed.
- **When an LLM reads traces for you,** ask for hypotheses over a named sample, with examples and counts - not "find the root problems", which returns confident prose you can't count - and read the cited examples, which are often invented. Do the first open-coding pass yourself. Tools built for this turn a vague question ("is it reward hacking?") into a rubric and count how often it occurs (Transluce's Docent, open source; the `error-analysis` skill in Husain and Shankar's evals-skills).
- **Measure what the agent actually reads.** Count which skill and reference files it opens across trials, and check whether incidental details of examples get copied (SKILL.md Section A: *Few-Shot Examples*, and the instruction-files bullet in *Context Engineering*).
- **Optional: a feedback channel for the agent.** Give it a tool to report what was slow, broken or unclear while it runs ("some junk, but some pure gold", one team), treat the reports as data, and notice what they leave out (Anthropic's *Writing effective tools for agents* also has eval agents give feedback on the tools). Ask for feedback, not reasoning (see the `reasoning_extraction` caveat above); read the provider's thinking summaries for the reasoning.

## Writing Evaluation / Judge Prompts
When using LLMs to evaluate outputs (LLM-as-judge), the prompt design differs from system prompts:

**Scale design:**
- Binary (pass/fail) is most reliable. 3-point scales (0/1/2) work well for nuance. Avoid 10-point scales without extensive anchoring.
- Define each score level explicitly with concrete examples of what qualifies.

**Structure:**
- Decompose complex criteria into sub-criteria (G-Eval approach). Ask the judge to evaluate each sub-criterion before producing a final score - and **keep per-criterion scores and comments visible instead of trusting one aggregate.** Similarweb lost a week reverting a good prompt change because two criteria (source breadth vs. attribution) moved in opposite directions inside the average; the per-criterion comments showed it immediately. Give every criterion explicit score anchors (what 0.0 / 0.3 / 0.8 / 1.0 look like), return a short gap + one-sentence reason per criterion, and check criteria for conflicting incentives (e.g. conciseness rewarded more clearly than completeness shortens reports that needed depth). The same holds across a bank of separate judge questions: two questions can pull one verdict in opposite directions (in one team's bench, a question asking the output to state an unsettled basis as "unknown" made a held-out question about undecoded fields come back "no" on the same lines in 3 of 3 judgings: the judge read the "unknown" sentence as a field decoded only by guess), so read the bank as a whole when you add a question.
- **One fact per question.** Split compound criteria into yes/no questions that each check a single fact: decomposed checklists raised agreement across 12 judge models by 0.45 and cut score variance (CheckEval, EMNLP 2025, arXiv:2403.18771), and in one team's bench a compound gross-or-net question gave unstable verdicts between judgings at three successive bench versions, then didn't split once across seven judgings after it became four one-fact questions. Grade each criterion in its own judge call, and give the judge an "Unknown" answer for when the evidence is missing (Anthropic, *Demystifying evals for AI agents*).
- Match the method to the output: golden answers work for focused questions; long-form outputs need anchored rubrics, **faithfulness checks** (does each claim follow from the retrieved data?), and **A/B judgment against an accepted baseline** rather than isolated absolute scores.
- Require reasoning BEFORE the score, not after, and **discard the reasoning** - parse only the verdict. Chain-of-thought in judges reduces randomness. When the judge model is actually thinking (always on for Claude Opus 5.5 / Fable 5.x, Kimi K3.x on Moonshot, and Grok 4.5+; on by default for GPT/Gemini at non-minimal effort and other Claude 5.x - but not Haiku 5.5 with thinking disabled, Sonnet 5.5 at `between_tools`, or Bedrock K3.x at `none`), native thinking already gives you reasoning-before-verdict; ask for the verdict (plus at most a short rationale field after it) rather than "write out your reasoning in `<thinking>` tags" or a `reasoning` field before the score, which Claude Opus / Sonnet / Fable 5.x can decline (and bill) as `reasoning_extraction`.
- Give the judge a concrete, checkable rubric ("The answer must mention 'Acme Inc.' in the first sentence; if it does not, grade 'incorrect'"). One criterion may need several rubrics for a holistic grade.
- Use structured output (JSON) for scores to ensure parseable results.

**Calibration:**
- Provide 2-3 few-shot examples per score level showing realistic edge cases (+25-30% accuracy improvement).
- Don't count on low temperature for consistency - current frontier models reject it or discourage it. Get stable scores from a tight rubric, binary or 3-point scales, structured output, and repeated runs (majority vote or mean).
- **Record the why in every human label.** Each label carries the decision, the evidence, the reason and the rule ("Fail: unsupported refund promise. Evidence: 'Your refund will arrive tomorrow', no confirmed payment date. Why: the user may rely on an invented commitment. Rule: promise dates only when the payment system confirms them.") - a bare FAIL teaches the next grader, human or model, very little (TensorOps, [Autonomous Engineering meetup talk](https://youtu.be/c6UNK1RPnIA), Nov 2026).
- **Expect criteria drift.** Graders' criteria change as they see more outputs - they add criteria and reinterpret old ones (Shankar et al., *Who Validates the Validators?*, UIST 2024, arXiv:2404.12272) - so version the rubric, re-judge the baseline when it changes, and don't compare scores across rubric versions.
- **Pre-register how undecided grades count.** Decide before grading whether "unknown", "can't tell" or abstaining grades count as fails, passes, or are excluded, and report both readings: in one team's bench, 11.6% of item-grades stayed undecided after a re-grade, and counting them against the claim gave -13.1 points where excluding them gave +4.9.
- **Decide how a split judgment counts.** With two judge sessions per question, one team counts a critical question as failed only when both say no, and re-judges a split once; it cut false fails caused by judge noise. Whatever rule you pick, fix it before grading and apply it to every arm.
- Report a judged pass rate corrected for the judge's error rates (see *Reporting a judged pass rate* below).

**Bias mitigation:**
- **Position bias**: In pairwise comparisons, randomize output order and average across positions.
- **Self-preference**: Use a different model as judge than the generator (reduces bias 10-25%).
- **Pick the judge model by measuring it on your labelled items.** Judge models differ more than their benchmark ranks suggest: in one team's comparison on Bedrock (Nov 2026; 72 settleable labelled items, each judged 3 times in fresh sessions), Kimi K3.1 Pro's majority verdict matched the label on 71 for $7.24, GPT-6.1 Sol on 67 for $2.03, and Grok 4.7 on 54 for $9.99, with 16 "unknown" majorities and lower run-to-run agreement (0.76-0.80 vs 0.93-0.98). The set had no evidence-missing items, so whether a judge abstains correctly was untested - include such items if abstention matters.
- **Judge repeatability**: a judge can be accurate on average and still flip on identical input. Score the same traces several times and measure variance as well as agreement with human labels (LangChain's "signal value" = accuracy × repeatability). In one study, repeated LLM judges agreed with the human label 80-99.8% of the time depending on the model, while a small typed decision model (returning a choice or probability, not text) matched 100% at ~1/80th the cost - cheap enough to score every production trace. Such **decision models** are now offered directly: Google's Gemini Decision 1 (Decisions API, Nov 2026) answers isolated yes/no, choice and rubric-score questions with calibrated probabilities and zero output tokens, and LangChain's `langchain_core.decisions` wraps decision models as a common interface (`gemini.md`, *Decisions API*; `langgraph.md`). A calibrated probability still needs a threshold you set on your own labeled examples, weighing a false pass against a false fail. Calibrate any judge by hand-labeling real traces, running the judge, and iterating on its prompt where it disagrees; a miscalibrated judge is worse than none because it gives false confidence.
- **Verbosity bias**: Add explicit length controls or penalization.
- **Hedging bias**: Judge practical effect on the user, not tone. "Did the response actually reject the broken premise, or just add a disclaimer before answering it anyway?"
- **Gameability**: test the judge against degenerate outputs - an empty answer, gibberish, a bare opener such as "Thought process:" - before you trust it or optimize against it. Such "master keys" drew positive verdicts from general and dedicated judge models (arXiv:2507.08794), and Karpathy describes an RL run whose judge scored the output "dhdhdhdh" at 100% (Dwarkesh Podcast, Oct 2025). An optimizer pointed at a judge finds these.
- **Don't grade by the chain-of-thought**: a model's stated reasoning is a scratchpad that *influences* the answer, not a faithful audit of it — models verbalize an outcome-changing hint only ~25–39% of the time (Anthropic, arXiv:2505.05410). Judge the *output* against the requirement; don't score correctness by how plausible the reasoning looks, and don't rely on visible CoT as a safety monitor.

**Anti-pattern:** Vague criteria like "rate the quality 1-10" produce inconsistent results. Specific criteria ("Does the response identify the factual error in the premise? Score 0 if it engages without pushback, 1 if it flags concerns but still answers, 2 if it makes the error the central point.") produce reliable judgments.

**Anti-pattern — judge prompt overriding the fixture's ground truth.** When fixtures carry explicit specs (e.g. `tools_required: [X, Y]`, `tools_forbidden: [Z]`, `expected_facts: [...]`), the judge prompt should treat those as the ground truth for that fixture — not as suggestions to weigh against its own opinion of what's correct. Concrete failure mode observed in a production bench: the judge prompt included "for procedure/test/dental queries: BOTH tools must be called in parallel" as a general rule. For 7+ adversarial fixtures that explicitly list `tools_required: [get_user_policy]` only (the test is "don't engage the fabricated premise"), the judge applied its own routing override and scored tool_use=0 even though the agent perfectly matched the fixture spec. Fix: remove the override, make the fixture's `tools_required` literally the ground truth. Result: 7 of 7 affected fixtures moved up (+0.8 to +2.2 each) with zero agent change. **When a judge has an opinion about what "should" be true, but the fixture spec says otherwise, the fixture wins** — otherwise the bench measures judge bias, not agent quality.

**Where to look for this**: any judge-prompt clause that begins "for [topic] queries..." or "if the question involves [X], the answer should..." — these are universal overrides that fire across all fixtures regardless of their specific spec. Audit those clauses against fixtures of the matching topic; if some fixtures legitimately need different behavior than the override prescribes, the override is wrong.

## Gate classifiers and action reviewers

A gate classifier is a judge that runs before an action instead of after an output: it allows or blocks a tool call an agent is about to make. Two published designs show how to build one: Anthropic's *How we built Claude Code auto mode* (anthropic.com/engineering), and the guardian review prompts in OpenAI's open-source Codex CLI (`prompts/templates/guardian/` on GitHub). When to ask and who can approve are covered in `agent-harness-patterns.md`.

- **Put cheap tiers in front of the classifier.** In Anthropic's design most calls never reach it:
  - a fixed allowlist of tools that can't change state (file reads, searches) runs first, with the user's own allow rules;
  - file edits inside the project come next, since version control makes them reviewable;
  - only the rest goes to the classifier: shell commands, web fetches, file operations outside the project, subagent spawns.

  On entering auto mode it drops the user's broad allow rules that grant arbitrary code execution (blanket shell access, a wildcarded script interpreter). Left active, they would keep the most dangerous commands away from the classifier.
- **Choose what the classifier sees.** Anthropic shows its classifier only the user's messages and the bare tool-call payloads.
  - It strips the agent's prose so the agent "can't talk the classifier into making a bad call".
  - It strips tool results because they are where injected text enters.
  - With both included, the classifier did worse on Anthropic's set of real overeager actions.
  - With tool calls alone, it lost the user's intent and blocked actions the user had plainly asked for.
  - The cost of stripping tool results is provenance: the classifier can't tell whether a target came from a query or was made up.

  That design is for command-style actions whose payload shows their effect. A browser or computer-use click doesn't: a coordinate says nothing about which recipient is selected. Codex's reviewer judges those actions from the observed interface state and selections. Pass that state as evidence that can't grant authorization.
- **Score separate axes, then derive the verdict.** Codex's reviewer rates the user's authorization (high, medium, low, unknown) and the action's risk (low to critical) separately, then applies written outcome rules. A single "is this OK?" mixes the two and drifts.
- **Write what not to block next to what to block.** Classifiers over-block what looks scary, so both designs carry explicit exceptions.
  - Anthropic's exceptions:
    - installing packages the repository already declares;
    - standard credential flows;
    - pushing to the session's own branch.
  - Codex's exceptions:
    - a path outside the workspace on its own;
    - a user-requested `rm -rf` of a target that a read-only check showed is empty. This one needs a reviewer that can see that check's result, which a classifier with tool results stripped can't.

  Anthropic's template checks block rules, then exceptions, then user intent, then decides. Its customizable parts are the environment (what counts as inside the trust boundary), the block rules and the exceptions.
- **Judge the effect, not the label.**
  - Evaluate the payload a script writes and then runs.
  - Treat a chain of commands joined with `&&` as one action.
  - Evaluate a command assembled by code as the assembled command.
  - Ignore what the agent says the action is for, and judge a browser click by its result on the actual page.
- **Say which way missing evidence pushes.** In Codex's reviewer, truncated or omitted content makes the verdict more cautious, but doesn't raise the action's intrinsic risk by itself. Earlier verdicts are context, not precedent.
- **Use two stages with one prompt.**
  - Anthropic's first stage is a single-token filter told to err toward blocking; it blocked 8.5% of benign actions.
  - Only what it flags goes to a second stage, with the same prompt except a final instruction to reason; that brings false blocks down to 0.4%.
  - Because the inputs match, the second stage reads almost entirely from the cache.
  - The post describes this on Sonnet 4.6. On a model that thinks natively, the second stage's reasoning comes from thinking: ask for the verdict, not for written reasoning (*Writing Evaluation / Judge Prompts* above). A first stage with no reasoning needs a model that can answer without thinking, such as Haiku 5.5 with thinking disabled (`claude-sonnet-haiku.md`).
  - A verdict in the first output token parses fast, but only fits two cases:
    - a first stage whose flags go to a reasoning pass. Codex's first-pass reviewer is one: it runs alongside the agent without blocking, and a "high" verdict turns on blocking review for later actions;
    - a model that thinks before it answers.

    Otherwise the model commits before it reasons (SKILL.md, *Output Format*).
- **Measure both error rates on real data.** Measure false blocks on real traffic, and misses on a set of real overeager actions taken from transcripts. Anthropic's pipeline misses 17% of real overeager actions. Most misses saw the danger but misjudged whether the user's consent covered this action. Prompt changes didn't fix that at an acceptable cost, so keep the riskiest actions behind hard rules in code.
- **Return a denial the agent can act on.** Send the block back as a tool result with its reason and an instruction to find a safer path, not to route around it. Cap repeated denials, then escalate to a human: Anthropic stops at 3 consecutive or 20 total.
- **Screen what the agent reads, too.** The classifier never sees tool results, so injected text can still steer the agent itself. Anthropic adds a probe on the input side: when a tool result looks like an injection attempt, it puts a warning next to the result that tells the agent to go back to what the user asked.
- **Check hand-offs too.** A subagent sees the orchestrator's instruction as the user's request. Anthropic runs the same gate on the subagent's own calls, checks the task at delegation, and reviews the subagent's actions at return, in case content it read compromised it.
- **Cheaper gates:** a calibrated decision model (see *Judge repeatability* above) or a framework guard such as LangChain's `AutoModeMiddleware` (`langgraph.md`) can serve as the first stage, with a threshold set on your own labeled actions.

## Reporting a judged pass rate

A judge's pass rate is biased by the judge's own errors. Measure its true-positive and true-negative rates (sensitivity and specificity) on human-labeled items, say which class counts as "positive", and report the corrected rate with the Rogan-Gladen estimator, θ = (p_obs + TNR - 1) / (TPR + TNR - 1), with a confidence interval that carries both the test-set and the calibration-set error (*How to Correctly Report LLM-as-a-Judge Evaluations*, arXiv:2511.21140; Husain and Shankar's `judgy` package implements it). A weak judge (TPR + TNR barely above 1) gives an interval too wide to use, and a lenient judge that rarely says "fail" can look accurate on a mostly-passing set; a judge that never fails anything tells you nothing.

**Don't compute the correction on the calibration set itself.** Rogan-Gladen applied to the same items you used to measure TPR and TNR returns exactly that set's human-label share, whatever the judge's errors (θ reduces to the true prevalence algebraically), so it can't show anything. Cross-fit instead: split item stems into folds, fit TPR and TNR on one fold, correct the pass rate on the other, and bootstrap stems within folds for the interval (one team's lesson after an in-sample correction looked like a validated result).
