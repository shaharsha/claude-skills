Applies to the **Claude model family** wherever it runs: the Anthropic API, AWS Bedrock (and Claude Platform on AWS), Google Cloud (Vertex AI / Google managed, and since Oct 22 2026 *Claude Models on Google Cloud (Anthropic managed)*), and Microsoft Foundry. The platform does not change prompt engineering - the model version does.

On the Claude API, Bedrock, Claude Platform on AWS, both Claude Models on Google Cloud options, and Foundry (Anthropic infrastructure); retirement not before Nov 9 2027. ## The 5.5-generation API contract (Opus 5.5 + Sonnet 5.5 + Fable 5.1 / 5.2)

Opus 5.5, Sonnet 5.5, Fable 5.1 / Mythos 5.1, and Fable 5.2 / Mythos 5.2 share a stricter API contract than Opus 5 / Sonnet 5 / Fable 5. (**Haiku 5.5 adopts most of it but not all** - it accepts forced `tool_choice` and `thinking:{type:"disabled"}`; see `claude-sonnet-haiku.md`, *Prompting Haiku 5.5*.) Code that ran on the previous generation can **400** or **go silent** on these without a prompt change:

- **Thinking is always on** (Opus 5.5, Fable 5.1, Fable 5.2). `thinking:{type:"disabled"}` and `thinking:{type:"enabled", budget_tokens:N}` both return 400. Omit `thinking` (or send `{type:"adaptive"}`); **`effort` is the only depth/cost control**. **Sonnet 5.5 is the exception:** its lowest setting is `thinking:{type:"between_tools"}` - no up-front thinking, but the model still writes progress notes between tool calls. `disabled` returns 400 (the message points to `between_tools`); `between_tools` is accepted only at effort `low`/`medium`/`high` (400 at `xhigh`/`max`), takes no other field (`display`, `budget_tokens`, `block_binding` → 400), and blocks per-message effort changes (400 if the level differs). In a request **without tools**, `between_tools` means answering with no thinking at all - use adaptive thinking for reasoning tasks. Responses may begin with `thinking` blocks (empty text at the default `display:"omitted"`), so select content blocks **by `type`, not position**, and pass thinking blocks back unmodified in tool loops.
- **No forced tool use.** `tool_choice` of `{type:"any"}` or `{type:"tool", name:…}` returns 400 (also on the token-counting endpoint); only `auto` and `none` remain. Anthropic's rationale: a forced call would skip thinking and the model would reason inside the tool arguments, degrading them. For schema-valid JSON use `tool_choice:auto` + **strict tool use** (`strict:true`) or **Structured Outputs**; to make the model call a tool, *say in the prompt when it applies* ("Use the `get_weather` tool to answer") - Opus 5.5 and Fable 5.1 follow explicit tool instructions reliably.
- **Thinking blocks are bound to the model and the conversation.** Replaying a thinking block after anything before it changed - the `system` prompt, the `tools` array, an earlier message, even different bytes behind an image URL - fails the **prefix check** and returns 400 (`bound to a different conversation`). **Who gets the 400** (Claude API, `prefix_mismatch_behavior` unset): **every account on Fable 5.2 / Mythos 5.2** and on Mythos 5.1 (on Bedrock, Mythos 5.1 accepts edited turns); on Fable 5.1, Opus 5.5, Sonnet 5.5, and Haiku 5.5, only accounts created on or after **Aug 31 2026** - older accounts get no error and the failing blocks reach the model. So history-editing code that runs clean on an older account can start failing the day it moves to Fable 5.2. The Message Batches API drops failing blocks instead of returning 400. Request fields outside `system`, `tools`, and `messages` (`effort`, `max_tokens`, `output_config`, `tool_choice`, `metadata`, `thinking.display`) and `cache_control` markers are not part of the check. Opt into `thinking.block_binding.prefix_mismatch_behavior:"drop_block"` (beta `thinking-binding-controls-2026-08-01`) to drop instead of fail - a stopgap while you fix the edit, because the model thinks again where blocks were dropped and output tokens rise - and log `input_transformations` to find where your harness edits history. **Treat every conversation as append-only**: change instructions/tools with mid-conversation system messages, per-turn reminders with turn-scoped system messages, and trimming with server-side compaction / context editing. Anthropic expects future models to enforce the check for all accounts, so adopt the pattern now. **Cross-model reads** (Claude API, and for Fable / Mythos 5.2 also Claude Models on Google Cloud (Google managed); every model reads its own blocks): **Fable / Mythos 5.2 read every other model's blocks** (Opus 5 / 5.5, Sonnet 5.5, Haiku 5.5, Fable / Mythos 5 and 5.1, and earlier Opus, Sonnet, and Haiku models), and **no other model reads 5.2's**, Fable 5.1 and Opus 5.5 included; Fable / Mythos 5.1 read Opus 5, Opus 5.5, and Fable / Mythos 5; Opus 5.5 reads Opus 5, Sonnet 5.5, and Haiku 5.5 but no Fable / Mythos; Sonnet 5.5 reads Haiku 5.5 but not Opus 5 / 5.5 or any Fable / Mythos; Haiku 5.5 reads none of the other models named here. All of these read Sonnet 5 and earlier Opus / Sonnet / Haiku blocks, and none of those earlier models (nor Opus 5 or Fable / Mythos 5) reads the newer ones. A router or fallback that moves a turn to a model that can't read the blocks silently drops that reasoning for those turns (not billed); the reasoning comes back when the conversation returns to a model that can read it, as long as your client keeps the blocks in history. Blocks from **Sonnet 5.5, Haiku 5.5, Fable 5.2, and Mythos 5.2** are also **bound to the producing account** (or a linked one) - another account's request drops them without an error. `block_binding` works only with adaptive thinking, so under `between_tools` keep history append-only or strip thinking blocks from the edited turn onward.
- **Fable 5.2's four breaking changes from Fable 5.1** (Anthropic's *What's new in Claude Fable 5.2*): (1) the prefix check above applies to every account (no change if Claude Code, claude.ai, Managed Agents, or the Agent SDK builds your requests); (2) only Fable / Mythos 5.2 read Fable 5.2's thinking blocks, so a fallback to Opus 4.8 or Opus 5 (its permitted refusal fallbacks), Opus 5.5, or Fable 5.1 loses that reasoning; (3) `computer_20251124` returns 400 on every platform except Bedrock - declare `computer_toolset_20260801`; (4) with the advisor tool, a Fable / Mythos 5.2 executor accepts only a Fable / Mythos 5.2 advisor (Fable 5.1 → 400), while a `claude-fable-5-2` advisor is accepted by every executor and returns its advice encrypted. Changing the advisor's `model` edits `tools`, so do it in new conversations. As on Fable 5.1, in an organization with **customer-managed encryption keys (CMEK)** structured outputs (strict tool use and JSON outputs) aren't available on Fable / Mythos 5.2 - leave out `strict` and validate tool input in code (new only if you come from a model other than Fable / Mythos 5.1). Also new: with the **MCP connector**, a server that returns a different tool list on a later request invalidates 5.2's thinking blocks unless the list is pinned (beta `mcp-client-2026-09-15`, Claude API only - Fable 5.1 and Opus 5.5 don't check this, so test against 5.2 itself); and the record-only mode (the binding header without `block_binding`) isn't available.
- **Text between tool calls now arrives as progress-update `thinking` blocks** (at most one before each tool call), not `text` blocks - empty at the default `display:"omitted"`. **No error, but a UI that streams narration goes silent.** Set `thinking.display:"updates"` (beta `thinking-display-updates-2026-08-18`) to receive progress updates while reasoning stays hidden, or `"summarized"` for both mixed; render each non-empty `thinking` block before the `tool_use` it precedes. (Fable 5 already did this; Opus 5 and Sonnet 5 did not.) On Sonnet 5.5 only notes longer than a sentence or two move into thinking blocks - short remarks stay `text` - and under `between_tools` the notes come back with their summary text without any `display` setting.
- **Computer use** on Opus 5.5 and Sonnet 5.5 (Claude API and Google Cloud) and on Fable / Mythos 5.2 (every platform but Bedrock) accepts only the `computer_toolset_20260801` toolset - the older `computer_20251124` tool returns 400 (still works on Bedrock).
- **Advisor tool pairings narrowed:** a Sonnet 5.5 executor accepts only Mythos/Fable 5.x, Opus 5/5.5, or Sonnet 5.5 as advisor (Opus 4.7/4.8 and Sonnet 5 → 400), and every accepted advisor returns its advice encrypted (`advisor_redacted_result`).
- **New cache-preserving controls** (beta, supported on all of these and Haiku 5.5): **per-message effort** - a `role:"system"` message with empty content and `output_config:{effort:…}` changes effort *without* breaking the cache (`mid-conversation-output-config-2026-07-01`). Placed directly after a `user` turn with new input it sets the level for the reply to that turn; anywhere else it takes effect from the next `user` turn with new input (a turn of only `tool_result` blocks doesn't count), and **the change is sticky** - "the new level then holds until a later message changes it." Now also on Bedrock for Fable 5.1, Mythos 5.1, and Opus 5.5; a top-level effort change restarts the cache and, on Fable 5.1, steers less reliably. **Turn-scoped system messages** - `clear_at:"next_user_message"` on a mid-conversation system message gives it system authority for one turn only; you keep sending it verbatim, it costs no input tokens once cleared, and the cache/thinking stay valid (`mid-conversation-system-clear-at-2026-08-21`). Use them for every per-turn nudge instead of inject-then-delete. Also: define tools inline in a mid-conversation message (`inline-tools-2026-09-15`) and **compaction on demand** (`compact-2026-09-04`).
- Unchanged from the 5 generation: non-default `temperature`/`top_p`/`top_k` → 400 (any value at all under API version `2026-10-21`); assistant prefill → 400; interleaved thinking automatic; raw chain of thought never returned. Minimum cacheable prompt **512 tokens**. Text output carries Anthropic's statistical watermark (EU AI Act; no tokens or characters added).

## API version `2026-10-21` (sampling params removed everywhere)

Anthropic shipped API version **`2026-10-21`** (Oct 21 2026) with new SDK majors (Python 2.0, TypeScript 1.0, Go 2.0, Java 3.0, C# 13.0, Ruby 2.0, PHP 1.0, `ant` CLI 2.0; now Apache-2.0). What changes for prompts and requests:
- **`temperature`, `top_p`, and `top_k` return 400 on every model, "even at the parameter's default value"** - including models like Sonnet 4.6 that used to accept them: "a request that lowered `temperature` for more consistent output loses that effect. No other setting replaces it." The SDKs no longer expose them. Consistency now comes only from prompting, Structured Outputs, and evals.
- `document` blocks in `assistant` messages → 400 (send documents in `user` turns); `citations` on `text` blocks in `user` messages (including inside `search_result` blocks) → 400.
- `MessageParam` becomes a union that includes `SystemMessageParam` - mid-conversation `role:"system"` messages are now typed. Client-side compaction in the TypeScript/Ruby tool runner is removed in favor of server-side compaction.
- On Bedrock, `2026-10-21` works only for Claude 4.7 and later; older models stay on `2023-06-01`.

Effort names are **not comparable across models** - always run a fresh effort sweep on your own evals after a model change; never port a setting.

|---|---|---|---|---|
| **Opus 5.5** | adaptive, always on | No (400) | **`medium`** | Start at `medium` (≈ or > Opus 5 at `high` on coding/knowledge work); `low` often comes close at much lower cost; reserve `xhigh`/`max` for measured gains |
| **Fable 5.2** / Mythos 5.2 | adaptive, always on | No (400) | `high` | Start at `high` (set it explicitly), then run evals at `medium` and `xhigh` too. `low` for quick back-and-forth, well-specified tasks, and fast subagents (Anthropic: its `low` scores sat close to Fable 5.1's at higher levels); `medium` for interactive coding, chat, everyday knowledge work; `high` for hard coding, research, long unattended runs - "most of the gain in capability is already present at `high`"; `xhigh` only where measured (slightly higher scores, many more tokens); `max` for ceilings and open-ended problems |

Things that hold across the current models:

- **Effort is the main lever for thinking, cost, and latency** - lower effort first when you want less thinking; it's more reliable than prompt instructions. Effort applies to *all* output tokens (text, tool calls, thinking): lower effort means fewer, terser tool calls.
- **Opus 5.5 thinks more per turn at a given level** than Opus 5 (most at `xhigh`/`max`), yet finishes tasks in fewer tokens overall. Keeping your Opus 5 effort value means longer turns.
- **`max_tokens` is a hard cap on thinking + reply** even when thinking isn't returned. Size it for the thinking: 64k is a sane start at `high`+; Anthropic reports 128k (the max) works well for long agentic coding turns on Opus 5.5.
- **Chat products: delete "think carefully before answering" lines** on Opus 5.5 - the model decides its own depth and effort is the control; removing the line made replies start sooner with no clear quality drop in Anthropic's testing. In multi-turn chat Opus 5.5 sometimes re-examines earlier answers on short follow-ups; if you want earlier answers treated as settled, append: *"Once you have answered something, treat that answer as done. On later turns, focus your thinking on what the user is asking now, and don't go back over an earlier answer unless the user asks about it or points out a problem with it."* (Leave it out where re-examination is valuable - long analyses, agentic work - and test that it doesn't suppress self-correction you need. **On Fable 5.2 it measurably does:** at `high` these sentences cut thinking on follow-ups but made the model "far less likely to point out mistakes in its earlier answers".)
- **Don't ask the model to write its reasoning into the output - anywhere.** On Fable 5.2, Fable 5.1, Opus 5.5, Opus 5, Sonnet 5.5, and Fable 5, a prompt that asks for the model's thinking in the output can be declined with the **`reasoning_extraction`** refusal - and a refusal before any output **is billed**, with no fallback model, so fix the prompt rather than retrying. Anthropic's list of triggers: "A `<thinking>`, `<reasoning>`, or scratchpad section that the model fills in before it answers; a `reasoning`, `thinking`, or `trace` field in JSON output or in a tool input; the model's private notes, or a running log of its reasoning; reasoning asked for verbatim or in full" - and "the wording can sit in a system prompt, a skill, or a tool description, so check those too." What still works: "Ask for a short explanation, the evidence behind a result, or a summary of the actions it took," and read `display:"summarized"` thinking blocks to see the reasoning. (Anthropic rewrote its own computer-use sample accordingly: "Explicitly show your thinking" became "State in one sentence what the screenshot shows and whether the step succeeded.")
- Adaptive-thinking triggering is steerable. If a large system prompt makes the model think more often than you want: *"Thinking adds latency and should only be used when it will meaningfully improve answer quality - typically multi-step reasoning. When in doubt, respond directly."* For time-to-first-token on Opus 5.5 at `low`: *"Answer directly without deliberating."* (measure quality). That line doesn't stop Fable 5.2 from thinking at `medium` and above (Sonnet 5.5 and Haiku 5.5 ignore such lines too; see `claude-sonnet-haiku.md`) - lower effort for those turns instead.
- Thinking content is omitted by default (`display:"omitted"`). Options: `"summarized"` (reasoning summaries + progress updates), `"updates"` (progress updates only, beta).
- **Steer thinking with general guidance, not a script.** Anthropic's best-practices page: *"think thoroughly"* often beats a hand-written step-by-step plan - Claude's reasoning frequently exceeds what a human would prescribe. To aim interleaved thinking: *"After receiving tool results, carefully reflect on their quality and determine optimal next steps before proceeding."* For overthinking (revisiting decisions, multiple threads): *"When you're deciding how to approach a problem, choose an approach and commit to it. Avoid revisiting decisions unless you encounter new information that directly contradicts your reasoning."* - then lower effort if it persists.
- **Self-check instructions are model-dependent.** "Before you finish, verify your answer against [test criteria]" still catches errors reliably on most Claude models (coding, math). On **Opus 5** Anthropic says it causes over-verification - remove it rather than rewrite it; presumably the same holds on Opus 5.5, which self-verifies and uses Opus 5 prompts as its baseline `[inference - not stated for 5.5]`. **Fable 5.x is different:** for long runs Anthropic recommends making verification explicit via *separate, fresh-context verifier subagents* at a set interval ("Establish a method for checking your own work at an interval of [X]... verifying your work with subagents against the specification") - external checks beat self-critique there. (Fable 5.2 already starts reviewer subagents on its own at `xhigh`/`max`, so check for duplicate review rounds before adding your own.)

## Cost and intelligence: Anthropic's measured playbook

From *Optimizing for cost and intelligence* (Anthropic-internal benchmarks - directional; measure on your own traffic). In order of what to try:

1. **Turn on caching and trim tokens** - free, and cache reads are routinely the largest single cost component in agent loops (see *Caching*). Defer rarely-used tool definitions behind **tool search** (`defer_loading`): with up to 502 MCP tools attached, full loading nearly doubled cost while deferred loading stayed flat - 45% cheaper at the same accuracy. **Keep data files out of the prompt:** a 1,862-row CSV pasted inline (~91K tokens) got Sonnet 5 to 6/25 correct aggregate answers; uploaded via the Files API and queried with code execution it got 25/25 at ~1/12 the cost.
2. **Audit prompts against the current model.** Opus 4.8-era prompts cost 36% more per ticket on Opus 5 with no accuracy gain; the audit made Opus 5 14% cheaper *and* lifted accuracy 92% → 97%. Instructions the new model follows too literally ("verify twice", "be maximally thorough", mandatory step scripts) cost money; text that no longer fits (a retired thinking setting, contradictory rules, a hand-rolled `<scratchpad>` fighting native thinking) costs 7-11 accuracy points each. Claude Code ships `/claude-api prompt-audit`, which reports model-mismatched prompt text and proposes a diff; audit tool descriptions and skills too.
3. **Compare models on cost per *solved* task, and price the tail.** Fable 5.1 at `low` solved 88.6% of a SWE-bench Pro subset at $0.54 per solve vs Sonnet 5's 77.4% at $0.84 - despite 5× the per-token price; but Opus 5 matched Fable 5.1 at the default for ~15% less, so rankings flip by workload. Anthropic's starting suggestion for most agent workloads: the frontier model at `low` effort, raised where it misses. Judge on the hardest ~10% of tasks - failed tasks still bill, then retry.
4. **Sweep effort before adding architecture.** On research/knowledge-work benchmarks the curve is nearly flat (`low` gave up 1-3 points for a third to half off; the default bought nothing over `medium`); on long-horizon coding, effort genuinely buys accuracy. **Run at low effort and re-run only the failures at a higher setting** when outcomes are checkable - same pass rate at about half the cost (paid for in latency on the failures).
5. **Budgets and caps do different jobs.** A **task budget** (advisory, the model sees it) cut cost per task 44% for ~3 points on SWE-bench Pro - start near your loop's p90 token use and set it once, on the first request. **`max_tokens`** is only a safety cap - lowering it doesn't lower cost per *solved* task (64k covered all but 2 of ~14,000 turns). On Managed Agents a **session budget** is the hard dollar stop. Set all three.
6. **Ask for the answer you'll read.** Output tokens cost 5× input and re-enter context every later turn: a one-line `DECISION | LABEL | REASON` triage answer used 39% fewer output tokens than a two-line format and a five-section memo used 6× as many - all at the same accuracy.
7. **Only then combine models.** **Advisor** (a cheaper executor runs the loop and consults a frontier model via the beta advisor tool): pays when the capability gap is real *and the executor actually consults* - a low-effort executor can stop noticing it's stuck and score below itself alone; prompt for ~one consult before substantive work and one before finishing, and measure the consult rate. **Orchestrator** (frontier lead, cheaper workers): paid off only as insurance against a cost tail on routine work, or for inputs larger than one context window; in every other measured case the lead model alone at lower effort was cheaper. (Anthropic's *Which Claude model should you build with?*, Nov 2026, adds one: an Opus 5.5 lead over up to 25 Sonnet 5.5 workers cost about a third less than Opus 5.5 alone, at about the same score, on a defect search over ~22M tokens of source - work far larger than one window.)
8. **When a model falls short, escalate in this order** (same post): "1. Check that the model can verify its own work, with a test, a build or a script that calls the endpoint. 2. Raise effort one level. 3. Move to the next model up, starting at a lower effort level than you used on the smaller one." Past `high`, one more effort level can cost as much as a bigger model: on FrontierCode 2.0, Fable 5.2 at `high` scored about level with Opus 5.5 at `max` (45.3% vs 45.5%) for roughly half the cost per task. And if one system runs several models, "build every request for the strictest of them": append-only history, `tool_choice:auto` with strict tools, content blocks read by `type`, and prompts and tool descriptions precise enough for the most literal model - so a step can move tiers without a code change; when the routing rule is simple, let code pick the model.

## Few-shot examples and reasoning in the output

SKILL.md's cross-model default is to skip few-shot chain-of-thought on reasoning models. **Claude is still the documented exception for examples - but no longer for `<thinking>` tags:**

- Ordinary few-shot guidance is unchanged - Anthropic still calls examples "one of the most reliable ways to steer Claude's output format, tone, and structure" and recommends **3-5** relevant, diverse examples in `<example>` tags. Don't strip them from a Claude prompt on the strength of the reasoning-model rule. (Fable 5.1's fix for unmarked quotations is itself a single worked example.)
- **Examples still shape the reasoning, but present them as method, not as a transcript of thinking.** Anthropic's best-practices page (revised Oct 2026) now reads: *"Multishot examples work with thinking. Worked examples in your prompt shape how Claude approaches similar problems in its own thinking blocks. Present each example as a problem, the method to apply, and the expected answer."* The old advice to put `<thinking>` tags inside few-shot examples was **removed** - on the 5.x models above, examples that model a written-out reasoning section invite the `reasoning_extraction` refusal. Rewrite existing `<thinking>`-tagged examples as problem → method → answer.
- **Manual chain-of-thought only with thinking off:** "When thinking is off, you can still encourage step-by-step reasoning by asking Claude to think through the problem before it answers, and to put the final answer in `<answer>` tags… On Claude Fable 5.1, Claude Fable 5, Claude Opus 5.5, Claude Opus 5, and Claude Sonnet 5.5, rely on thinking instead, at a lower effort level if cost or latency matters."
- **Structured outputs:** don't put a `reasoning` / `thinking` / `scratchpad` property before the answer on these models - "A property that asks for the model's thinking or step-by-step reasoning might lead to a `reasoning_extraction` refusal. Ask for a short explanation instead" (e.g. a one-sentence `rationale` after the verdict). Native thinking already happens before the output, which is what SKILL.md's reasoning-before-answer schema rule is for.

The tool-usage case cuts the other way: for the Claude 5 generation, examples showing *how to call* a tool constrain exploration, and an expressive schema beats them. See SKILL.md §B, *Input Examples*.

## Sampling parameters and prefill (removed)

Setting `temperature`, `top_p`, or `top_k` to any non-default value returns **400** on Opus 4.7 and later, Sonnet 5, and every Claude 5.x model. Omit them. `temperature = 0` never guaranteed identical outputs anyway - for determinism, constrain the output with Structured Outputs, strict tools, enums, and explicit format rules. Haiku 4.5 doesn't document the 400, but omit sampling params there too.

Prefilling the last assistant turn is unsupported on Claude 4.6+ and all 5.x models (400). Replacements: force output format → Structured Outputs; skip preamble → "Respond directly without preamble"; continue an interrupted response → move the partial text into the user turn and ask the model to continue.

## Task budgets (beta)

A `task_budget` gives Claude a rough token target for a whole agentic loop (thinking + tool calls + results + output); the model sees a running countdown and paces itself. Beta header `task-budgets-2026-03-13`, `output_config:{effort:…, task_budget:{type:"tokens", total:N}}`, minimum 20k. **Advisory**, not a hard cap (`max_tokens` is the hard per-request ceiling the model never sees). Too tight a budget makes the model cut corners; for open-ended quality work, don't set one. On Opus 5.5, a *time* signal (see `claude-opus.md`, *Prompting Opus 5.5*) is the analogous lever for multi-agent wall-clock.

## Literal instruction following

Claude 4.7+ interprets prompts literally, especially at lower effort: it will **not silently generalize** an instruction from one item to another or infer requests you didn't make. If you need an instruction applied broadly, state the scope (*"Apply this formatting to every section, not just the first one."*). Fable 5.1 follows explicit tool instructions reliably - which is what replaces forced `tool_choice`.

## Verbosity, tone, and formatting

Length is model-specific: Opus 4.8 calibrates to task complexity; Opus 5 runs long; Opus 5.5 is reported clearer and less wordy; Fable 5.1 can run *dense*; Fable 5.2 follows style rules closely (a hard sentence-length cap makes it choppy, per Anthropic's [Prompting Claude Fable 5.2](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2#review-instructions-written-for-earlier-models) - see `claude-fable.md`, *Prompting Fable 5.2*, for its report block). If your product needs a fixed style, prompt for it explicitly - positive examples of the right concision beat "don't be verbose", and one brief instruction (*"lead with the outcome; be selective about what you include rather than compressing into fragments"*) beats an enumeration on the 5.x models. For a warmer voice: *"Use a warm, collaborative tone. Acknowledge the user's framing before answering."*

**Your prompt's formatting leaks into the output** - a markdown-heavy prompt pulls markdown-heavy replies; if steering isn't working, match the prompt's style to the output you want (strip markdown from the prompt to get less of it). XML format indicators also work (*"Write the prose sections in `<smoothly_flowing_prose_paragraphs>` tags"*).

Formatting defaults: the models **default to LaTeX** for math (if you don't render it: *"Write all math in plain text: `/` for division, `*` for multiply, `^` for exponents; no `\( \)`, `$`, or `\frac{}{}`"*). Earlier models over-used markdown lists and bold; **Fable 5.1 leans the other way** - so audit anti-formatting rules on migration and replace them with a rule for when formatting helps. Instruct positively (*"write in flowing prose paragraphs; reserve markdown for code and headings"*) rather than "don't use markdown."

## Tool use and subagents

- **Forced tool use is gone on Opus 5.5 / Sonnet 5.5 / Fable 5.1 / Fable 5.2** (see the API contract; Haiku 5.5 still accepts it, at the cost of skipping thinking). Say when a tool applies in the prompt or the tool description; use strict tools / Structured Outputs for schema guarantees.
- **Try one agent with skills before subagents.** Anthropic's *When to fold subagents into your main agent loop* (Oct 2026): "a single agent with skills frequently outperformed both the one-prompt-for-everything design and the subagent design on quality, and often at a lower cost and latency per task" - typically "one clear system prompt, 4-5 thin data tools, and firm output guardrails." Split into subagents when a single loop shows measurable degradation from context bloat, when tasks need parallel fresh windows, or when one agent can't pick tools reliably or carries conflicting instructions - and **divide by context, not by problem type** (splitting by problem type creates a "telephone game"). Group tools by user intent: "once you exceed 30-50 tool definitions in the system prompt, tool choice tends to degrade" - use tool search with deferred loading past that. And avoid the **"Frankenprompt"**: "Every team adds a sentence to the system prompt, resulting in conflicting rules and no consistent voice" - give the system prompt one owner.
- **Managed Agents dynamic workflows** (beta, Oct 2026: `multiagent_20261001` with `workflows` enabled) let the agent start parallel workflow runs itself; "tell it in its system prompt when to start a run" (Anthropic's example: *"When you're asked to review more than a few contracts, start a workflow run that reads them in parallel and combines the findings. Review one or two contracts yourself, without a run."*). "There's no approval step before a run starts, so nothing enforces this" - gate cost in the harness.
- **Phrasing decides whether Claude acts or advises.** "Can you suggest some changes?" gets suggestions; "Change this function to…" gets the edit. Set the default explicitly with one of Anthropic's two blocks: `<default_to_action>` (*"By default, implement changes rather than only suggesting them. If the user's intent is unclear, infer the most useful likely action and proceed, using tools to discover any missing details instead of guessing."*) or `<do_not_act_before_instructions>` (*"Do not jump into implementation or change files unless clearly instructed to make changes. When the user's intent is ambiguous, default to providing information, doing research, and providing recommendations rather than taking action."*). Pick one - never both.
- **Structured outputs / strict tools - mechanics:** use `output_config.format` - the old `output_format` parameter is deprecated (400 without the `structured-outputs-2025-11-13` beta header); Structured Outputs are now GA on Bedrock for the 5.x models too. The first request with a new schema pays grammar-compile latency (compiled grammars are cached 24h); objects must set `additionalProperties:false`; no recursive schemas, no complex types inside `enum`, array `minItems` only 0 or 1; the feature injects its own system prompt (a few extra input tokens), and changing `output_config.format` invalidates the prompt cache for the whole conversation - fix the format at the start.
- The 5.x models trigger required tools reliably; raising `effort` is the main lever to increase tool use (lower effort = fewer, terser calls). If a tool is under-used, describe explicitly when and why to use it - in the tool description (SKILL.md §B: on Claude 5, delete the system-prompt duplicate).
- **Parallel calls:** for maximum parallelism: *"If you intend to call multiple tools with no dependencies between them, make all the independent calls in parallel. Never use placeholders or guess missing parameters."* On Fable 5.1 agent loops, use the per-turn batching nudge in `claude-fable.md`, *Prompting Fable 5.1*.
- **Progress narration** now lives in thinking blocks on the 5.5 generation - see the API contract above and the progress-update levers in each model's file (`claude-opus.md`, `claude-fable.md`, `claude-sonnet-haiku.md`). Remove "after every N tool calls, summarize progress" scaffolding written for older models; describe the cadence you want instead. (Exception: on Fable 5.2, when the harness can't append turn-scoped reminders, Anthropic recommends the one-line *"Every few tool calls, give the user a one-line update on where things stand."* - see `claude-fable.md`, *Prompting Fable 5.2*.)
- **Subagent defaults differ by model:** Opus 4.8 spawns fewer; Opus 5 and Fable 5/5.1 spawn more readily; Fable 5.2 follows the harness (rarely with a minimal spawn tool, readily where prompts invite delegation, and it self-reviews with subagents at `xhigh`/`max`). Give explicit guidance either way:
  ```
  Do not spawn a subagent for work you can complete directly in a single response.
  Spawn multiple subagents in the same turn when fanning out across items or reading multiple files.
  ```
  On Fable 5.1, prefer non-blocking orchestration (lead keeps working while subagents run); on Opus 5.5, time signals increase useful parallelism.
- **Managing tool context - four levers, each for a different source of bloat** (Anthropic's *Manage tool context*): **prompt caching** of tool definitions from day one (pays back on the second hit); **tool search** (`defer_loading`) once the toolset passes ~20 tools - definitions load only when Claude looks them up; **programmatic tool calling** - Claude writes one script that calls several tools inside Anthropic's code-execution sandbox, so intermediate results never enter history (docs report 24% fewer input tokens on agentic search with a higher score); **context editing** to clear stale `tool_result` blocks in long conversations. They compose. Caveat from Anthropic's own measurements: context editing only pays on genuinely long sessions (on a short run it cost 74% *more*), and a hand-written prune at task boundaries - replace big stale tool results with a one-line extract at the tail - beat it because it caches better; clear in a few large batches, not many small ones.
- **Tool changes mid-session:** declare every tool (including a `send_to_user` tool) from the **first request** - adding to `tools` later edits the prefix and invalidates thinking on the 5.5 generation. Use mid-conversation tool changes / inline tool definitions instead.

## Long context and documents

For 20k+ token inputs, put the documents at the top and the query/instructions at the end (up to ~30% better on complex multi-document inputs), and wrap each document with its metadata:

```
<documents>
  <document index="1">
    <source>annual_report_2023.pdf</source>
    <document_content>{{ANNUAL_REPORT}}</document_content>
  </document>
</documents>
```

Then ask for relevant quotes first (in `<quotes>` tags) and the analysis second - quote-grounding keeps Claude on the relevant spans. Use consistent, descriptive tag names across prompts and nest tags where content has a natural hierarchy.

## Caching

**Caching is opt-in** - a request with no `cache_control` caches nothing. Either set the top-level **automatic caching** field (`cache_control:{type:"ephemeral"}` on the request - each request caches the conversation so far) or place explicit `cache_control` breakpoints. The prefix is hashed in order **tools → system → messages**, byte-exact; place stable content first, append new messages at the end, never reorder. Check `cache_read_input_tokens` for hits - Anthropic sees a median **84%** of agent-loop input read from cache (top harnesses 94%+); **below ~80%, something is breaking the cache.** Anthropic's measured cache-breakers: any per-request text (timestamp, queue position, status line) *ahead of* the stable prefix - a 25-token status line at the top of the system prompt took one run from $0.59 to $4.24, worse than no caching (put per-request text in the newest user turn); changing `effort` or thinking config; any system-prompt edit; setting or changing the structured-output format (invalidates the **whole** conversation); adding, removing, or reordering a tool; changing a task budget mid-task; each context-editing pass. Make cache-invalidating changes at natural breaks (e.g. the first request after compaction), and on Fable 5.1 / 5.2 remember a cache write costs ~50× its read price.

- **Cache-read price is now model-specific:** 0.1× input on most models, including Haiku 5.5; **0.05× on Opus 5.5** ($0.20 vs $0.50 on Opus 5) **and Sonnet 5.5** ($0.10, since Oct 7 2026); **0.025× on Fable 5.1** ($0.25, a quarter of Fable 5's) **and Fable 5.2** ($0.20). Cache reads are most of the bill on agentic/coding workloads, so these cuts matter more than the headline price - and cheaper reads shift the compaction trade-off later. Writes: 1.25× (5-min) / 2× (1-hour).
- **Minimum cacheable prompt:** 512 tokens on Fable 5.2 / Mythos 5.2, Fable 5.1 / Mythos 5.1, Opus 5.5, Opus 5, Sonnet 5.5, Haiku 5.5, and Fable 5 / Mythos 5; 1,024 on Opus 4.8, Sonnet 5, and Sonnet 4.6; 2,048 on Opus 4.7; 4,096 on Opus 4.6 / 4.5 and Haiku 4.5. Caches are isolated **per workspace** on the Claude API, Claude Platform on AWS, and Foundry (per organization on Bedrock and Google-managed Google Cloud) - split traffic across workspaces and you split the cache.
- **Most of what breaks the cache also breaks thinking** on the 5.5 generation: per-turn inject-and-delete, summarizing turns in place, and editing `system`/`tools` mid-session. Use turn-scoped and mid-conversation system messages instead. **Effort is the exception:** a top-level `effort` change restarts the cache but leaves thinking valid (effort isn't part of the checked prefix); per-message effort keeps both.
- **Message threads (beta, Nov 2 2026, `message-threads-2026-08-12`)** keep a conversation on the server so each later request sends only the new messages plus `thread:{type:"continue", previous_message_id:…}` - lower, steadier time to first token on long agent loops. **`system` and `tools` come from the create request and must be left out of continue requests**, so instruction and tool changes go in as mid-conversation system messages / inline tools, as above. Threads are best-effort (expire 5 minutes after the last request; a continue returns 404 once gone), so keep your own full history and a replay path; caching is still opt-in per thread (top-level `cache_control`). Not ZDR- or HIPAA-eligible.

## Mid-conversation system messages

A `role:"system"` message placed in `messages` (after a user turn, subject to placement rules) appends updated instructions partway through a conversation **without restating the system prompt** - earlier turns stay byte-identical, so cache hits survive and 5.5-generation thinking stays valid. Available since Opus 4.8 on Opus 4.8+, Opus 5/5.5, Fable 5.x, and Sonnet 5.5 - **not on Sonnet 5** (nor per-message effort or mid-conversation tool changes) - no beta header. Extensions (beta): **turn-scoped** (`clear_at:"next_user_message"`) for one-turn reminders; **effort-only** messages (empty content + `output_config.effort`) for per-message effort; **inline tool definitions** (`tool_addition` blocks). This is now the default way to change anything mid-run on Claude. Rules and patterns from Anthropic's docs: a system message that carries content (`text`, `tool_addition`, or `tool_removal` blocks) must immediately follow a `user` turn (or an `assistant` turn ending in a server tool result) and be the last entry or be followed by an `assistant` turn - **any other position, including between a `tool_use` and its `tool_result`, returns 400**; an empty, effort-only message is accepted anywhere. Later system messages override earlier ones and the top-level `system`. Use it to state operator-level facts the app observed (files changed, auto-approve toggled, budget dropped). **Relaying what the user typed mid-loop:** Anthropic's docs **no longer list this as a use for system messages** (changed Oct 2026): "On Claude Sonnet 5.5 and Claude Haiku 5.5, deliver the user's words in the user turn instead. These models are trained to resist prompt injection through tool results, so they can treat a system message placed right after a tool result as untrusted text and ignore it." The pattern, on all current models: **append the user's words as a text block in the user message that carries the `tool_result` blocks, after the last one; never put user text inside a `tool_result`; keep harness notices in a separate system message; and in interactive sessions don't inject your own token/budget countdown after every tool result** (it provokes the same misread; task budgets haven't been seen to). **Phrase it as context, not a command** ("new input arrived from the user: X", "the remaining budget is now Y") - Claude resists instructions that seem to work against the user even from the system role, so "ignore what the user said" works worse than stating what changed. Never use it to pass tool output or retrieved documents - that third-party content stays in `tool_result` blocks.

## Fast mode

`speed:"fast"` for up to ~2.5× output speed from the *same model* at premium pricing (Opus 5.5 fast: $8/$40). **GA for Opus 5.5 since Oct 15 2026** - no beta header, a default fast-mode rate limit in the Start/Build/Scale tiers, and available on the Claude API, Foundry, and Claude Models on Google Cloud (Anthropic managed). **Fable 5.2 has fast mode too ($16 / $80, ~2× its standard price; Fable 5.1 had none):** Messages API requests on the Claude API, both Claude Models on Google Cloud options, and Foundry (Anthropic-hosted deployments, as the separate model `claude-fable-5-2-fast`); Mythos 5.2 on the Claude API. On Foundry, send fast requests to the `-fast` deployment and leave out `speed` (setting `speed` on the non-`-fast` deployment errors). Not in Managed Agents - remove `speed` (and the `fast-mode-2026-02-01` header if you send it) there. On Opus 5 and Opus 4.8 it's still a research preview (beta `fast-mode-2026-02-01`). Haiku 5.5 is not a fast-mode model. Throughput, not quality - use it for latency-sensitive interactive surfaces, not to save cost.

## Refusals, safeguards, and fallback

A classifier decline is **not an error**: HTTP 200 with `stop_reason:"refusal"` and a `stop_details` object naming the category. Handle it explicitly and configure fallback - server-side (`fallbacks:"default"`, beta, retries on the model Anthropic recommends for that category), SDK middleware, or your own retry. Whether a pre-output refusal is billed now **depends on its category** (it counts against rate limits either way) - check Anthropic's *How refusals are billed*.

- **Categories** (`stop_details.category`): `cyber`, `bio`, `frontier_llm` (helping develop competing AI models - restricted by the commercial terms; benign ML work can trip it), `reasoning_extraction`, `general_harms`, or `null` for an unnamed policy area. Display `explanation`, don't parse it. A refusal can arrive **mid-stream after partial output** - discard the partial text; a mid-stream refusal bills the input and the output already streamed.
- **Opus 5.5:** cyber (source-code vuln finding allowed; high-risk dual-use cyber blocked), **bio** (new vs Opus 5; same as Fable 5.1; everyday health questions unaffected; research orgs apply to the Life Sciences Verification Program), and **`reasoning_extraction`** (new) - server-side fallback does **not** retry that one; fix the prompt instead (stop asking for reasoning in the reply).
- **Fable 5.2:** the same five categories; Anthropic reports ~55% fewer blocks than Fable 5.1 (~60% fewer in cyber, ~40% in bio), and its announcement says blocked queries get a response from Opus 4.8 (cyber) or Opus 5 (bio). Permitted fallback targets: Opus 4.8 and Opus 5 - and a fallback can't read 5.2's thinking blocks, so that turn runs without the earlier reasoning.
- **Fable 5.1:** same categories as Fable 5, with fewer false positives at launch. Triggers of false positives: compile-check phrasing (ask "Are there any bugs in this program?" instead of "Does this compile?"), lesser-known languages (give it the language docs), **base64 in tool output** (remove it).
- **Opus 5:** cyber classifiers (far milder than Fable's) plus `reasoning_extraction` (no fallback - fix the prompt); cyber declines fall back to Opus 4.8.

## Agentic and long-horizon work

- **Context awareness:** Sonnet 5 / 4.6 / 4.5 and Haiku 4.5 are documented as tracking their remaining context window, and without guidance may wrap up early as it fills. If your harness compacts or saves state, say so: *"Your context window will be compacted as it approaches its limit… do not stop tasks early due to token budget concerns. Save progress to memory before the window refreshes."* Prefer server-side compaction over client-side rewrites on the 5.5 generation - Anthropic's compaction overview (Oct 2026): "Use on-demand compaction wherever it is available" (still beta, `compact-2026-09-04`); threshold compaction doesn't keep thinking in turns you re-insert on Fable 5.1 / Opus 5.5 / Sonnet 5.5 / Haiku 5.5. If you compact client-side, replace the whole history with one summary + the new user turn so no stale thinking replays. Haiku 5.5 gets no context-awareness tags - use a task budget if it should pace itself.
- **Multi-window tasks:** first window sets up scaffolding (tests, `init.sh`), later windows iterate against a todo list and structured state (`tests.json`). A fresh window often beats compaction - Claude rediscovers state well from the filesystem and git.
- **State:** structured JSON for trackable state, freeform notes for progress, git for checkpoints; a todo/checklist the model updates is also what your harness uses to detect early stops (Opus 5.5).
- **Autonomy and safety:** *"Take local, reversible actions (editing files, running tests) freely, but for destructive or externally-visible actions - deleting files/branches, force-push, posting to shared systems - ask first. Never use destructive shortcuts like `--no-verify`."* Opus 5.5 scores best yet on Anthropic's behavioral audit (much less likely to take hard-to-reverse or out-of-bounds actions), but keep the harness gate. Fable 5.1's "finish the task" block adds a useful guard: before a state-changing command, check that the evidence supports that specific action - a pattern-matched failure can have a different cause.
- **Scheduled / unattended automations** (Anthropic's *Building effective agent automations*, Oct 2026): "Read each source from a bookmark, not a fixed time window. Report a failed read as unreadable, never as a quiet day. Re-check every item right before posting. Count a post as sent only when Slack confirms it, then update bookmarks and ledger. Re-read your preferences every run, from a store the agent can't edit. Give the agent read-only access wherever it only reads, and cap what each run can spend." Don't bake a copy of user preferences into the prompt - "it keeps applying rules you've already changed."
- **Make "done" observable:** the Claude Code team's review practice - "We give Claude something it can run—like tests, a build or a screenshot to compare against the design—and ask it to show the output instead of saying it's done. Then a subagent reviews the diff with fresh context."
- **Constrain what web fetch may open.** Managed Agents' `web_fetch` now fetches only URLs that already appeared in the session (`url_not_in_prior_context` otherwise); on the Messages API the `url_sources` parameter (with `web_fetch_20260318`) lets you exclude sources - e.g. drop a code-execution tool's output so URLs Claude itself printed can't be fetched. This is the exfiltration guard for agents that read untrusted content.
- **Ground coding answers in the code:** `<investigate_before_answering>` *"Never speculate about code you have not opened. If the user references a specific file, you MUST read the file before answering…"* - one of the few places Anthropic's own sample keeps a MUST.
- **Don't let it game the tests:** for coding agents, ask for a general-purpose solution that works for all valid inputs, not just the test cases; no hard-coded values or special-case helper scripts; *"If the task is unreasonable or infeasible, or if any of the tests are incorrect, please inform me rather than working around them."* Pair with *"It is unacceptable to remove or edit tests"* when tests are the spec. If scratch files are unwanted: *"If you create any temporary new files, scripts, or helper files for iteration, clean up these files by removing them at the end of the task."*
- **Research agents:** give explicit success criteria, ask for cross-source verification, and for complex research: *"Search for this information in a structured way. As you gather data, develop several competing hypotheses. Track your confidence levels in your progress notes to improve calibration. Regularly self-critique your approach and plan."*
- **Prompt chaining still earns its place** when you need to inspect, log, or branch on intermediate outputs - most commonly draft → review against criteria → refine as separate calls - even though adaptive thinking and subagents now handle most multi-step reasoning internally.
- **Specify fully in the first turn.** The 5.x models use more tokens reasoning after each user turn in interactive sessions; state task, intent, and constraints up front and reduce human turns (matches the "one well-specified turn" finding in SKILL.md).

## Overengineering and scope

Claude can over-deliver - extra files, unnecessary abstractions, unrequested flexibility, extra tests. A scoped guidance block still earns its place at high effort: don't add features/refactors/"improvements" beyond what was asked; don't add docs or error handling for code you didn't change or scenarios that can't happen; no abstractions for one-time operations - *"The right amount of complexity is the minimum needed for the current task."* On Fable 5.1 use the "extras" instruction in *Prompting Fable 5.1* (`claude-fable.md`) (report pre-existing issues as follow-ups; size tests to the neighbors). On Fable 5.2, scope follows what the prompt says about code ownership - see *Say who owns the code* in `claude-fable.md`.

## Code review harnesses

The 5.x models find more bugs with fewer false alarms (Opus 5.5 reportedly caught 72% of known bugs at `low` vs Opus 5's 56% at `high` in one tester's eval `[single-source]`). A harness tuned for an older model that says "only report high-severity issues" / "be conservative" / "don't nitpick" gets followed faithfully - the model investigates as deeply but reports less, which looks like a recall drop. Separate finding from filtering: *"Report every issue you find, including low-severity and uncertain ones - coverage is the goal here; a separate step will rank and filter. Include a confidence level and estimated severity for each finding."* If you must self-filter in one pass, set a concrete bar ("bugs that could cause incorrect behavior, a test failure, or a misleading result").

## Frontend design

Claude has a persistent default house style - warm cream/off-white backgrounds (~`#F4F1EA`), serif display type, italic accent words, and on Opus 5.5 also numbered "01/02/03" section labels, monospace labels, and pill-shaped buttons. Generic instructions ("avoid a generic AI look", "no cream") mostly swap one default for another. What works: (1) **name the specific patterns to avoid** and iterate - check which defaults the first result used and extend the list (Anthropic's Opus 5.5 example: *"Do not use a cream or off-white background, italic accent words in headlines, numbered '01/02/03' section labels, monospace labels, or pill-shaped buttons."*); (2) specify a concrete palette/typography - explicit specs are followed well; (3) ask for 3-4 distinct visual directions first and let the user pick (this also replaces `temperature` for design variety).

## Vision and computer use

High-resolution images (up to 2576px / 3.75MP, coordinates 1:1 with pixels) since Opus 4.7. **Opus 5.5 reads dense charts, diagrams, and screenshots far more precisely without tools** - even at its lowest effort it beat Opus 5 at its highest on chart reading - including position-dependent meaning (which boxes an arrow connects, what changed between diagram versions). **Re-test and remove vision workarounds** built for earlier models. For the densest inputs (technical drawings, dense charts), two things still add accuracy on Opus 5.5 and Fable 5.1: higher-resolution images, and image tools - ideally a container with the raw images plus PIL/OpenCV so the model can crop, zoom, measure, and verify; a crop tool alone gets most of the uplift. The models use these tools better at higher effort. Downsample when fidelity isn't needed (cost). Computer use: 1080p is a good balance (720p / 1366×768 for cost); Opus 5.5 at default effort matched Opus 5's success rate at much higher effort, and requires the `computer_toolset_20260801` toolset on the Claude API / Google Cloud.
