## Prompting Fable 5.2 (and Mythos 5.2)

From Anthropic's *Prompting Claude Fable 5.2* (Anthropic-internal tests - directional; measure on your own tasks). **Make every change below in new conversations only:** the prefix check runs on every account, so a stored conversation resumed with edited `system` text or tools can return 400. Mid-conversation changes go in the newest turn or an appended system message. Anthropic's migration order: set `effort:"high"` explicitly and run evals at `medium` and `xhigh` too; read the prompts, skills, agent files, memory, notes, and harness text you carry over and remove or test the lines listed under *Review older instructions* below; run your longest agentic tasks and note where it stops early, asks for approvals it doesn't need, goes quiet, delegates more than needed, or adds to code you wanted restructured; then fix one behavior at a time, measuring effect and token cost.

- **Effort** - see `claude.md`, *Effort and thinking*. Don't carry over a level tuned on Fable 5.1 or Opus 5.5; rerun the sweep. At `high` and above it thinks before almost every reply, even a greeting, and effort barely changes reply length (use the prompt for length and tone). Prompt lines asking it to think less ("answer directly without deliberating", which Fable 5.1 usually follows) don't work at `medium`+; lower effort for those turns. To change level mid-conversation and keep the cache, use per-message effort; a top-level `effort` change restarts the cache.
- **Finishing the whole task.** On long multistep tasks it sometimes ends the turn with a list of what remains, an offer to continue, or a stop at an ordinary obstacle such as a timeout - more often at `low` / `medium`. Anthropic's system-prompt text, which separates ordinary obstacles (diagnose and work through them) from deliberate blockers (leave them alone and report):
  ```
  # Finishing work
  Please avoid stopping while you still owe work the user asked for. Be persistent and do not stop unless needed.

  While status notes are welcome, as is clarifying with the user on open decisions, carry on with work that does not depend on the user's answer without unnecessary stops.

  If you notice yourself inviting the user to redirect you or offering to wait, instead proceed on the next part of the task. You may meet ordinary obstacles like errors, timeouts, locked files, empty results or failing tools. Diagnose them first, and when they are not real blockers, work through them with the access you have (wait and retry, fix the request, use another tool or source) rather than stopping unnecessarily.

  If someone clearly decided something is a hard blocker, such as a file marked not to be touched, access that was intentionally withheld, or a safety guardrail, leave it alone, say plainly what you found, and look for another safe way to finish the task. Stopping before the task is complete is very rarely merited, as in when the task can't move forward without user input, or where the blocker is deliberate and should not be worked past. This does not override the need for confirmation on risky or destructive actions.
  ```
  On replayed agentic-coding sessions at `medium`, a version of it halved the sessions that ended with doable work left (it removed most ask-permission and offer-to-continue endings, not the list-what-remains ones), for ~30% more output tokens. It asks less with this text, so keep your own confirmation step for risky or irreversible actions.
- **Approvals are applied as written.** Give a specific go-ahead ("Yes, run the migration on the staging database"), not a bare "continue" or thumbs-up. Approval rules in the system prompt should name the exact actions they cover: one rule that listed "sending messages to people outside this conversation" among the steps needing approval made it hold back about half of its routine requests to colleagues and other teams.
- **Say who owns the code.** With nothing said about ownership, or with the code presented as someone else's, it adds to the existing structure (even repeating code) and reports nearby problems instead of fixing them. If you want it to improve structure as it works: *"This codebase is yours: what it's for and how it's built are your call, and you'll keep building on it."* - it merged repeated code in about half of tries vs under a tenth without it (the result held inside a long system prompt), but used ~1.5× output tokens, made unrequested changes (mostly tests and docs), changed an existing feature's behavior in one try in six to ten (more at higher effort), and its summary often left out small changes - review the diff, not only the summary. A scope-limiting rule elsewhere ("No drive-by refactors, renames or cleanups") doesn't cancel the sentence (it still merged code in about a third of tries), so leave the sentence out where the user owns the code and wants minimal change.
- **Keep users informed during long turns.** It can write little user-facing text during long tool runs, and may make its first tool call without saying what it's about to do. In order: (1) receive the updates - between-tool updates come back as progress-update `thinking` blocks, empty at the default `display:"omitted"`; set `"updates"` (beta `thinking-display-updates-2026-08-18`) or `"summarized"` and render the non-empty ones; (2) if you can change the harness, count consecutive tool steps with nothing to read (count with `display` set to `"updates"` or `"summarized"`) and after several append this as a turn-scoped system message: *"The user hasn't heard from you in a while: say in a few words what you're doing, then continue."* (roughly halved the longest silent stretch at no noticeable token or time cost; leave each reminder in `messages` afterwards - removing or rewording one invalidates later thinking); (3) for an opening line, brief updates, and a closing recap where a human watches: *"Before you start, say in a line what you're about to do; brief updates while you work help the user follow along. Close with a short recap that stands on its own (what you found, what you did, and what's next), so a reader who only sees the last message has the full picture."* (spoke before its first tool call every time; ~20% more output tokens); (4) if you can't change the harness or have no mid-conversation system messages: *"Every few tool calls, give the user a one-line update on where things stand."* (cut most long silent stretches). Expect runs of several tool calls between updates even so; on asynchronous work, where the user comes back for the result, the gaps matter less.
- **Subagents depend on the harness.** With a minimal spawn tool on short tasks it rarely delegates; in a product whose prompts invite delegation it delegates readily, and at `xhigh` / `max` it uses subagents to review its own work (Fable 5.1 didn't). First review the lines in your prompts, skills, and agent files that push delegation. Rewrite the spawn tool's description only if it still over-delegates: state what a subagent adds to a session's cost (first), when delegation is worth it and when not, and how to brief one - Anthropic's tested description cut delegation by about a third at the same task success. Check which model your harness runs subagents on; early testers liked Fable 5.2 as planner and orchestrator for other models.
- **Keep caution from piling up.** Cautious instructions accumulate in memory, notes, instruction files, and messages between agents, and Fable 5.2 follows them closely - it may ask for approvals it doesn't need or hold back routine work, mostly in multi-agent setups (in one setup only Fable 5.2 held back). Fixes, each measured on simulated tasks: **remove notes you no longer need** (one note saying never to retry, among a dozen, cut retries after a busy tool from nearly all to ~4 in 10); **name the steps that need no approval** (a line listing retries as needing no approval raised retries from almost none to about half, where a general instruction to act more freely changed nothing - name only calls that are safe to repeat); **check what reviewer agents attach** (a reviewer's "stop at the first error" stopped Fable 5.2 in about a third of tries; Fable 5.1 and Opus 5.5 retried); **write the exception into the rule itself** (an approved step under a "never" rule ran ~1 in 10 times, and a separate line saying an approved step has its go-ahead barely helped; when the rule itself said to get a go-ahead first, it ran ~9 in 10). Keep your own confirmation step for risky actions.
- **Review older instructions.** Reconsider, before migrating: standing delegation lines; **a token budget your harness writes into the prompt** (removing a large one lowered cost at equal performance at `high` / `xhigh` - this is prompt text, not the API's task budgets); **harness code that edits earlier turns** (shorten history with context editing or compaction that keeps no earlier turns after the summary; with `drop_block`, thinking dropped on every turn is the worst case for output tokens, and the cost grows with how often the harness edits); **Opus 5.5's "treat that answer as done" lines** (see `claude.md`, *Effort and thinking* - they made it far less likely to flag its own earlier mistakes); **think-less lines**; **hard style rules** (it follows them closely, so "one instruction per sentence, in 20 words or fewer" makes prose choppy - Anthropic, [*Review instructions written for earlier models*](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2#review-instructions-written-for-earlier-models)); and **accumulated rules, notes, and memories** - delete cautions whose reason no longer holds, rewrite absolute rules to state their scope and reason, and if a system is already stuck, restart it with trimmed memory (keep the originals).
- **Make reports easy to follow.** For final reports and handoffs after long agentic work, Anthropic's block (adjust to your readers):
  ```
  # Communicating clearly
  Write for an intelligent but low-context reader. The person reading has not seen your tool calls, your reasoning or the files you opened, and may be switching in from other work. Messages should generally be self-contained: the reader should understand what you mean without having to dig for other context. Put the key points in the first few sentences. Practice progressive disclosure in your sentence order, and do not use undefined references and ideas in line 1 that won't make sense until the reader reaches line 12.

  Use plain words, and write in clear, understandable full sentences. Do not use a term or abbreviation that you made up during the work. Say what the thing is in a way any reader would understand. Write mostly in the style of ASD-STE100 Simplified Technical English: short sentences, one idea per sentence, active voice, and consistently using the same word for the same thing. Use a paragraph of flowing prose where ideas connect, and keep bullets for lists of separate items. Leave out unnecessary details unless the reader asks and practice concision, but do ensure that your messages have the key context. Aim to make your user-facing text as human-readable and clear as possible.
  ```
  It made final reports less dense (fewer semicolons) and, on workflow tasks, shorter sentences. Remove hard style rules first.
- **Prompt injection runs through the fallback.** On Gray Swan's indirect-injection benchmark (system card, no product protections) Fable 5.2's attack success at k=15 was 4.09% vs 1.02% for Fable 5.1 and 0.96% for Opus 5.5 - mainly because cyber-classifier fallbacks sent 53% of attack attempts to Opus 4.8, which was compromised at 5.17% vs 2.05% on attempts Fable 5.2 answered itself (computer use: 7.69% of fallback requests compromised without probes, 1.02% with). If the agent reads untrusted content, keep your injection defenses on the fallback path too, not only on the primary model.
- **Refusals:** the same categories as Fable 5.1 (`cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms`); benign security and life-sciences work can trip `cyber` / `bio` (Anthropic's Cyber and Life Sciences Verification Programs; Mythos 5.2 for verified orgs). Anthropic reports ~55% fewer blocks than Fable 5.1 (~60% fewer in cyber, ~40% in bio). Permitted fallback targets: Opus 4.8 and Opus 5; `reasoning_extraction` has no recommended fallback, so fix the prompt. A fallback loses the 5.2 thinking blocks for the turns it serves.
- **Fable 5.1 prompt fixes on 5.2:** Anthropic's 5.2 guide doesn't say whether Fable 5.1 prompts carry over `[not stated]`. The fixes in *Prompting Fable 5.1* below target 5.1 behaviors the 5.2 guide doesn't list (the per-turn parallel-batching nudge, the async "operating autonomously" block, the "extras" scope instruction); keep each one only where your evals on 5.2 still show the behavior it fixes.

## Prompting Fable 5.1 (and Mythos 5.1)

Existing Fable 5 prompts perform well; these are the behavior deltas with Anthropic's fixes (full set in *Prompting Claude Fable 5.1*):

- **Parallel tool calling is more variable** in loops where the next independent reads are *implied* (custom coding agents, bash+editor harnesses, computer use) - it may issue one call per turn. Quality is unaffected, but every turn costs a round trip. Fix: append a **turn-scoped system message after each tool-results turn**: *"First privately list what you need next; then request every item that doesn't depend on another's result in this one response."* Leave earlier copies in place byte-for-byte (the API clears them); without the beta, put the sentence in a text block after the `tool_result` blocks.
- **Fewer progress updates** than Fable 5, especially at high effort and in long tool chains. First set `display:"updates"`; then **delete any "hold all findings for the final response" line** written for chattier models; only then add a cadence instruction (*"Before you start, say in a line what you're about to do; brief updates while you work help the user follow along. Close with a short recap that stands on its own…"*). If your UI hides tool output, tell it so via a turn-scoped message - otherwise it runs commands to "show" output the user never sees.
- **Denser prose** (longer sentences, fewer paragraph breaks). Define the anti-pattern rather than listing rules - Anthropic's paragraph on **"mannered prose"** (metaphor and flourish substituting for direct statement) works, and so does the short *"Please remove all mannered prose."* Prefer putting it in the user message.
- **Less formatting in chat.** It uses bold, headers, and lists *less* than earlier models, so legacy anti-formatting rules now over-suppress structure. Replace them with a rule for *when* formatting is appropriate (lists when asked or when the content is multifaceted; plain prose in conversational/emotional exchanges; minimal formatting when the user requests it).
- **Unmarked quotations when summarizing sources.** Fix with one complete worked example in the system prompt (request → correct response → one sentence on why it's correct: organized by agreement/difference, sources conveyed in the assistant's own indirect speech, at most a short *marked* quote).
- **Finish the whole task (async work).** Without a nudge it sometimes describes the next step instead of doing it, or asks permission for work already requested. Anthropic's two-block fix: (1) *"You are operating autonomously. The user is not watching in real time and cannot answer questions mid-task…"* - the opening sentence carries most of the effect - plus a check of the final paragraph before ending the turn (if it's a plan, list of next steps, or promise, do it now) and an exception for when the user is describing a problem or thinking aloud (deliver the assessment, don't apply a fix); (2) a "delivering work" block that makes the request the scope: don't quietly narrow, widen, or swap it; do everything not blocked by an open question; complete every unblocked part and say exactly what was left out. Can make it ask less on genuinely ambiguous requests - check the trade-off.
- **Scope and tests:** on open-ended features it may fix nearby code, extend behavior, or commit extra test files. An explicit "extras" instruction (report pre-existing bugs as follow-ups instead of fixing them; implement the most directly supported reading of ambiguity and state it; commit tests only where asked or where the repo already keeps them, ~one focused test per stated behavior) cut unrequested additions substantially with no loss in task success.
- **At `low` effort it searches less** and answers from memory more. Raise effort for the affected turns (per-message effort) or add: search before answering when a query centers on a name you don't confidently recognize or that comes from a fast-moving area (AI models, dev tools), including the name as the user wrote it - *"partial background is exactly what makes an out-of-date answer sound authoritative."*
- **Whole-file rewrites for small edits** - append *"The number of tokens used to edit files is best minimized, all else being equal. Therefore, when it will not affect the end result, try to surgically edit a file rather than rewrite the entire thing."*
- **Long deliverables at `xhigh`/`max`** can be drafted fully in thinking and then again in the reply. Prefer `high`; if you must go higher, size `max_tokens` for both and append Anthropic's note that the whole reply shares one ~`[max_tokens]` limit and that drafting the full deliverable twice doubles the turn without improving it.
- **Compaction summaries:** it follows explicit "what to preserve" lists well - Anthropic's client-side summarization instruction enumerates six things to keep exactly (difficulties and resolutions; options tried or set aside and why; decisions, constraints, preferences stated exactly; current state; open items and promises; hard-to-reconstruct details like names, numbers, links) and weights the user's words over the assistant's. Cheaper cache reads mean compacting early may no longer be the right trade - experiment with later compaction points.
- **Async subagents:** let the lead keep working while subagents run - the spawn tool returns immediately, results arrive in a later `user` message, and a separate tool lets the lead wait when it wants to. Lowers time-to-completion at similar cost.
- **Still true from Fable 5** (Anthropic says Fable 5 prompts carry over; the full set is in *Prompting Claude Fable 5*):
  - Turns run long (minutes at high effort, hours autonomously) - raise client timeouts, stream, and check runs asynchronously (scheduled jobs) rather than blocking.
  - Over-planning on ambiguous tasks: *"When you have enough information to act, act. Do not re-derive facts already established in the conversation, re-litigate a decision the user has already made, or narrate options you will not pursue in user-facing messages. If you are weighing a choice, give a recommendation, not an exhaustive survey. This does not apply to thinking blocks."*
  - **Ground progress claims** (nearly eliminated fabricated status reports): *"Before reporting progress, audit each claim against a tool result from this session. Only report work you can point to evidence for; if something is not yet verified, say so explicitly. Report outcomes faithfully: if tests fail, say so with the output; if a step was skipped, say that; when something is done and verified, state it plainly without hedging."*
  - **Checkpoints without enumerating cases:** *"Pause for the user only when the work genuinely requires them: a destructive or irreversible action, a real scope change, or input that only they can provide. If you hit one of these, ask and end the turn, rather than ending on a promise."*
  - **Final-summary readability** after long unattended work (dense arrow-chain shorthand, private labels, references to thinking the user never saw): tell it the final message is *"a re-grounding, not a continuation of your working thread: the outcome first, then the one or two things you need from them, each explained as if new... drop the working shorthand. Write complete sentences. Spell out terms... If you have to choose between short and clear, choose clear."*
  - **Give the reason, not only the request:** *"I'm working on [the larger task] for [who it's for]. They need [what the output enables]. With that in mind: [request]."*
  - **Memory:** give it a place to write lessons: *"Store one lesson per file with a one-line summary at the top. Record corrections and confirmed approaches alike, including why they mattered. Don't save what the repo or chat history already records; update an existing note rather than creating a duplicate; delete notes that turn out to be wrong."*
  - **Context-budget anxiety:** avoid showing a remaining-token countdown; if the harness must, add *"You have ample context remaining. Do not stop, summarize, or suggest a new session on account of context limits. Continue the work."*
  - **`send_to_user` needs an instruction:** defining the tool isn't enough - without *"Between tool calls, when you have content the user must read verbatim (a partial deliverable, a direct answer to their question), call the send_to_user tool with that content. Use send_to_user only for user-facing content, not for narration or reasoning"* it rarely calls it.
  - **Scaffolding:** separate, fresh-context verifier subagents outperform self-critique on long runs; skills written for older models are often too prescriptive and *degrade* its output - review them; state boundaries explicitly (it can take unrequested actions like drafting emails or defensive git backups).
- **Retention/fallback:** 30-day retention required (not ZDR-eligible unless Anthropic expressly authorizes). Permitted fallback targets for refusals: Opus 4.8 and Opus 5; fallback credit refunds the cache-switch cost.
