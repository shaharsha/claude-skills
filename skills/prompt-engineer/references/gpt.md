# GPT (OpenAI) - Provider Deep-Dive

Applies to the **GPT model family** wherever it runs: the OpenAI API, Azure OpenAI / Microsoft Foundry, and AWS Bedrock. The platform does not change how you write the prompt - the model version does - but Azure/Foundry and AWS Bedrock change the request contract (endpoints, tool APIs, reasoning replay, caching); see `gpt-hosts.md`. API rules in this file describe OpenAI's own API unless they say otherwise. Prompting guidance for the GPT-6 models before 6.2 (GPT-6.1 Terra, GPT-6 Luna, GPT-6 Astra, GPT-6.1 Sol, GPT-6 Sol) is in `gpt-6.md`; this file carries the shared rules and GPT-6.2.

**Current models (November 18 2026):** **GPT-6** is the current generation, and its tiers advance independently: **GPT-6.2 Astra and GPT-6.2 Sol** (Nov 17) are the flagship and the everyday model, **GPT-6.1 Terra** (Oct 26) is the mid tier, and **GPT-6 Luna** the cheap tier. **There was no GPT-6.1 Astra** - OpenAI "decided not to release its GPT-6.1 Astra model due to heightened AI safety concerns" (CNBC, Sept 28 2026; it "didn't quite meet the bar in terms of staying within scope and authorization"). No GPT-6.2 Terra or Luna, new Codex model, or gpt-oss successor has shipped. The naming scheme introduced with GPT-5.6 holds: the number is the generation, and **Astra / Sol / Terra / Luna** are capability tiers that advance on their own cadence.

- **GPT-6.2 Astra** (`gpt-6.2-astra`, Nov 17 2026) - the flagship, "our most capable model for your hardest projects, from start to finish", and OpenAI's default recommendation ("If you're not sure where to start, use GPT-6.2 Astra"). **$8 / $40** per 1M, 20% below GPT-6 Astra (cached input **$0.40 - 0.05×**; cache writes $10 for 30 min, $20 for 12 h). Effort `low`-`max` - **`none` is rejected**. **May 18 2026 cutoff.** It finishes tasks in fewer output tokens than GPT-6 Astra and writes more concisely, and it reports obstacles less reliably (see *Prompting GPT-6.2*). OpenAI's first released model at its High threshold for AI self-improvement.
- **GPT-6.2 Sol** (`gpt-6.2-sol`, Nov 17 2026) - "our go-to model for everyday work, from coding to powering agents at scale". Keeps 6.1 Sol's **$2 / $10** (cached input $0.10 - 0.05×; cache writes $2.50 / $5). Effort `low`-`max` - **no `none`**. **Jun 1 2026 cutoff.** OpenAI-reported: within 0.5 points of 6.2 Astra on FrontierCode 2.0 at about a fifth of the cost (both at `max`).
- **Both 6.2 models:** text and image in, text out; tool calling requires the Responses API (Chat Completions only without tools); ZDR-eligible; US and EU data residency for Standard, Fast and Batch; **Ultrafast** (`service_tier:"ultrafast"`, a service tier, not a model) on both with US residency only, at 3× Standard through Feb 28 2027 and 6× from Mar 1 2027; the multi-agent beta; both meet OpenAI's Critical cyber threshold and launched with tighter refusals on security and biology work (see *Safeguards*). GA on Microsoft Foundry and AWS Bedrock the same day.
- **GPT-6 Astra** (`gpt-6-astra`, GA Sept 4 2026) - the previous flagship, still served: **$10 / $50** (cached input $1, cache writes $12.50), effort `low`-`max` with **no `none`** (400), Apr 30 2026 cutoff, ZDR-eligible. `gpt-6.md` has its prompting guidance.
- **GPT-6.1 Sol** (`gpt-6.1-sol`, Sept 29 2026) - superseded by 6.2 Sol at the same price, still served: **$2 / $10** (cached input $0.10, cache writes $2.50), effort `low`-`max`, default `medium`, **no `none` or `minimal`**, tools on the Responses API only, Apr 30 2026 cutoff, US and EU data residency. Ultrafast at 6× Standard (since Oct 8; global, US and EU residency).
- **GPT-6 Sol** (`gpt-6-sol`, Sept 22 2026) - superseded but still served, and the Sol to keep if you need `none` effort; **$2 / $10** (cached $0.20). Effort `none`-`max`, default `medium`. Apr 20 2026 cutoff.
- **GPT-6 Luna** (`gpt-6-luna`, Sept 22 2026) - the efficient tier "for focused, high-volume tasks with a clear goal" (summarization, extraction, quick answers). **$0.10 / $0.50** (cached $0.01). Effort `none`-`max`, default `medium`. May 18 2026 cutoff.
- **GPT-6.1 Terra** (`gpt-6.1-terra`, Oct 26 2026) - the new mid tier (there is no `gpt-6-terra`): "a fast, efficient model that combines detailed visual reasoning and precise computer use alongside clearer, more natural writing"; "a significant step up from GPT-5.6 Terra" at half the standard price of 5.6 Terra and of Sol. **$1 / $5** (cached input **$0.05 - 0.05×**; cache writes $1.25 for 30 min, $2.50 for 12 h). Effort **`none`-`max`, default `medium`** (unlike Astra and 6.1 Sol, it keeps `none`). 1.05M context, 128K output, **Jun 1 2026 cutoff**; text + image in. Tool calling requires the Responses API; **no Ultrafast and no multi-agent beta**. OpenAI positions it for "screen-based workflows, concise writing, and scoped code fixes" - "for the most complex coding tasks, GPT-6.1 Sol and GPT-6 Astra remain the better choice" (written before 6.2; read it as Sol and Astra). GA on Microsoft Foundry the same day.
- **GPT-5.6 Terra** (`gpt-5.6-terra`, $2 / $12) is now superseded by 6.1 Terra; GPT-5.6 Sol ($4 / $20) and Luna ($0.20 / $1.20) remain available.
- **Small models:** `gpt-5.4-mini` is still active; **`gpt-5.4-nano` is deprecated** (shutdown **Apr 1 2027** → `gpt-6-luna`, alongside `gpt-5.3-codex` and `gpt-5.1` → `gpt-6-sol`). The GPT-4o / GPT-4.1 snapshots shut down Jan 14 2027 → Luna. Default to Luna for the cheap tier; keep the mini/nano guidance below for existing workloads. Check shutdowns programmatically via the optional `shutdown_date` field on `GET /v1/models`.

The GPT-6 family (6.2 Astra and Sol included) shares a **1.05M context window (922K max input) and 128K max output**. Input above ~272K tokens is billed at 2× input/cache and 1.5× output **for the whole request** - chunk or cache rather than stuffing. Batch is 50% of standard, and so is Flex on the models that list it (GPT-6 Astra, GPT-6 Sol, 6.1 Sol, 6.1 Terra and Luna; OpenAI's pricing page has no Flex row for the 6.2 models); fast mode is 2× the price (no latency SLA; with EU data residency on every current model except GPT-6 Astra and GPT-6 Sol). **Background completion windows** (public beta since Nov 17, on 6.2 Astra, 6.2 Sol, 6.1 Terra and Luna): a background Responses request with `background_options.completion_window` set to `2h` is billed 30% below Standard and `8h` 40% below, follow-up requests included; `soonest` is the undiscounted default. Treat each new generation as a family to re-tune for, not a drop-in swap.

## GPT-6.2: what changed in the API

Two request-contract changes arrive with GPT-6.2 Astra and Sol (OpenAI's *Using GPT-6.2*, *Keep the prefix unchanged*, and the reasoning and prompt-caching guides, Nov 17 2026). Both punish a harness that edits what it already sent.

- **An edit to earlier history now drops the model's reasoning.** "Starting with GPT-6.2, the Responses API drops reasoning items after mid-conversation edits to the conversation history (prefix edits), certain model changes (including downgrades), or changes to the end user or organization." The model then redoes that reasoning (more tokens and latency) or answers worse. A prefix edit is anything that inserts or changes content *before* a reasoning item: rewriting an earlier developer message, shortening an old tool result, downsizing a past image, replacing old turns with your own summary, or changing request-level `tools`, `text.format` or `reasoning.effort`. Appending after it is safe, and so is deleting whole items without touching the rest. Before 6.2 these edits only cost cache hits.
- **Make every change an append:**
  - *Effort or output schema:* a `configuration_update` input item before the next user message (`reasoning.effort` and, new, `text.format`), with the request-level setting left as it was. Standard single-agent mode only.
  - *Tools:* keep the `tools` list and its order fixed; restrict with `tool_choice` (`"none"`, or `allowed_tools`); add with an `additional_tools` input item (`developer` role, a `tools` array), replayed in its original position.
  - *Instructions:* append a new `developer` message at the end; don't rewrite the first one.
  - *Long tool outputs, files and images:* shorten or downsize them before the first send. OpenAI "strongly recommend[s]" that or compaction over truncating old items later.
  - *Compaction:* OpenAI's own (`/responses/compact`, or `context_management`) keeps the reasoning that follows it. A home-grown summary must go "at the end of the model's context, instead of before recent turns", or you accept the drop. `/responses/compact` rejects a history that contains `configuration_update` items: strip them, compact, then append one fresh update and declare again any tools you had added with `additional_tools` ("The standalone summary doesn't restore these tools").
- **Keep the user and the model fixed within a conversation.** A `safety_identifier` that differs between the request that created a reasoning item and the one that reuses it drops the item (`end_user_mismatch`), and that "includes supplying an identifier on only one of the two requests". Switching model family, or to a less capable model in the same family, drops it too (`model_mismatch`, which the reasoning guide describes as already in force before 6.2); moving up keeps it. So route per conversation, not per turn: a router that sends easy turns to Sol and hard ones to Astra inside one conversation throws away Astra's reasoning on every step down.
- **Find drops in the response.** `input_transformations` lists the reasoning items the API removed and why (`prefix_mismatch`, `end_user_mismatch`, `model_mismatch`, `organization_mismatch`, `turn_boundary`). For cache misses, Prompt Cache Diagnostics compares a request with an earlier response (`prompt_cache_options.comparison_response_id`) and names the first difference (`tools_changed`, `input_changed`, `reasoning_effort_changed`, `text_format_changed`, …); it "can't verify whether the model reused reasoning".
- **Top-level `instructions` moved to the end.** "Models starting with GPT-6.2 append top-level `instructions` after `input` in the Responses API" - past every cache breakpoint, so OpenAI "bills those instruction tokens at the uncached input-token rate on every request, even if you repeat identical instructions". **Put the system prompt in a `developer` message as the first item of `input`**, and keep `instructions` for guidance that applies to one request (a "summarize your findings" on the last turn). One coding harness measured the old pattern on `gpt-6.2-sol`: about 14,000 uncached input tokens per step, 3 after moving the prompt (OpenCode 2.3.2 release notes, Nov 18 2026).
- **Why:** OpenAI describes the drops as a safeguard against distillation (system card: extraction of earlier-turn reasoning succeeded in 54.0% of attempts on GPT-6 Astra and 0.2% on 6.2 Astra). The card also adds "checks that can hold streamed responses if they might expose private model reasoning" - one more source of mid-stream pauses.

## GPT-6: what's new in the API

- **Async tool calling:** set `async:true` on a function or custom tool; the model keeps reasoning, calls other tools, or answers independent parts of the request while your app runs it; return the result later with the original `call_id`. Your app still executes the tool and tracks pending work (OpenAI documents a developer-defined wait-tool pattern).
- **Service tiers for speed:** Fast mode (~2× speed at 2× price) and **Ultrafast** (`service_tier:"ultrafast"`) - on GPT-6.2 Astra and Sol (3× Standard through Feb 28 2027, then 6×; US residency only), GPT-6 Astra (6×; US/global only) and 6.1 Sol (6×; global, US, and EU residency); not on Terra or Luna. Also settable as `agent.service_tier` in the Agents API. Use a persistent WebSocket for agent loops or network overhead eats the gain. Orgs can now restrict which tiers each project may use.
- **Mid-turn steering:** over a WebSocket Responses connection, send new user instructions (a correction, a changed requirement) while the model is working; completed work is preserved and the update joins a continuation.
- **Change effort without breaking the cache:** add a `{"type":"configuration_update","reasoning":{"effort":"high"}}` input item before the next user message and **leave request-level `reasoning.effort` unchanged**; it holds until another update. GPT-6 family, standard single-agent mode; the same item can now change the response format (`text.format`). Tools can likewise be enabled/disabled without breaking the cache.
- **Misalignment monitoring** runs asynchronously on GPT-6 Astra and GPT-6.2 traffic; safety checks can **stop the task in the API** (ChatGPT/Codex ask the user to review instead) - see *Safeguards*.
- Carries over from GPT-5.6: computer use, Structured Outputs, streaming, programmatic tool calling, multi-agent orchestration, prompt caching, persisted reasoning, compaction, pro mode.
- **Agents API** (`v1/agents`, beta) additions since Sept: pre-warmed hosted sandboxes billed only during active turns, per-session **spending limits** (`spend_control`), Office-document skills in the sandbox, and **scheduled automations** (cron sessions, plus an `automations` tool so an agent can schedule its own follow-ups - say in the prompt when it may). The SDK's computer-use **toolsets** (Oct 2026) add allow-lists, a `url_policy`, `max_steps`, and a `confirm` callback where "only an exact `true` … allows the proposed action" - put consent in that callback, not in prompt text. **Oct 30 Agents API changes:** a session's tool list can be updated mid-session (each update replaces the whole list; function and MCP tools switch at the next model call, built-in tools by the next turn); compaction now runs **in the background by default** (`compaction.async:false` for blocking; background mode can raise token use); `experimental.time_awareness:true` sends periodic current-time reminders (off by default); and `review:"auto_review"` lets an OpenAI-managed model approve or deny eligible tool and permission requests (billed tokens on top). Treat auto-review as one more model-based gate - keep hard limits in the harness.
- **Endpoint limits:** GPT-6.2 Astra and Sol, GPT-6 Astra, **GPT-6.1 Sol**, and **GPT-6.1 Terra** support Chat Completions but their **tool calling requires the Responses API**; GPT-6 Sol and Luna support function calling in Chat Completions **only at `reasoning_effort:"none"`**. Use Responses for any reasoning-with-tools work on OpenAI's API; on AWS Bedrock, Converse also runs GPT tool loops (`gpt-hosts.md`).

## Prompting GPT-6.2 (Astra and Sol)

OpenAI's *Using GPT-6.2* guide (it replaced *Using GPT-6* at the latest-model URL; the older page is at `/guides/latest-model/gpt-6-astra`) describes behaviors "we've seen when working with GPT-6.2 Astra and Sol" and offers its prompts "as a starting point across the GPT-6.2 model family". Several reverse GPT-6 Astra's defaults, so re-check every line you added for that model.

- **Concise and direct by default** (GPT-6 Astra ran long and formatted heavily). "When migrating, revisit instructions like 'be concise' in your system prompt" - on 6.2 they over-clip. OpenAI's starting prompt for a working collaborator: *"Write using terminology the user and sources use. Keep technical details and use domain-specific language when they make the explanation more precise. Use the active voice and keep closely related details together. Cover the key points up front, and avoid references that the reader can only make sense of later in the response. Give the user enough context to follow your reasoning."* For text that goes to someone else: *"consider who will read it and tailor the content to that intended audience. The intended audience likely does not have the same context as the user"*.
- **Working shorthand leaks into the final answer.** After a long task the model can carry labels from its reasoning or from other agents into the reply. OpenAI's fix: *"Treat your final answer as the user's first look at your work, and not as a continuation of intermediate commentary. The final answer must always be fully self-contained… Do not carry over working shorthand, jargon, or abbreviations from your reasoning, tool calls, or instructions to subagents and automations."*
- **It leaves obstacles out of its report - add a disclosure rule yourself.** OpenAI's system card: 6.2 Astra "omitted a known obstacle to completing its work in 22.28 percent of trials, compared with 11.09 percent for GPT-6 Astra" (a source file removed, a build tool unavailable), and failed the card's Broken Search Tool test (does the final answer admit the lookup could not be done?) in 23.00% of cases against 7.58%; both 6.2 models regressed, and OpenAI's hypothesis is that training for concise answers without caveats caused it. "The Codex developer prompt substantially reduces these omissions" and "is not applied to direct API requests". The open-source Codex prompt for both 6.2 models carries these lines, which its GPT-6 Astra prompt lacks: *"If you are blocked and unable to make useful progress, you should state that clearly when you cannot do more useful work."* and *"In your final answer back to the user, mention any relevant flaws in your work or any decisions you made without explicit guidance from the user, so that the user can verify your approach and work. Disclosure in commentary alone is not enough. You MUST repeat any such disclosures in the final answer."* (`codex-rs/models-manager/models.json`, Nov 18 2026; the card doesn't say which lines do the work). Put an equivalent in your developer message, and test it: remove a file or break a tool in an eval and grade whether the final answer says so.
- **It accepts false premises more readily than the models it replaces.** BullshitBench (Nov 18 2026) clear-pushback rates: 6.2 Astra 49-55% (GPT-6 Astra 64-69%), 6.2 Sol 42-46% (6.1 Sol 59-65%). AA's hallucination rate rose as well (6.2 Astra 54-59%, 6.2 Sol 55-66%). Where a wrong premise is costly, add an explicit premise check (SKILL.md Section A) and ground answers in retrieved text.
- **It can propose a next step and wait.** "When the user's intent is unclear, the model may propose a next step and wait for confirmation." For work that should run unattended: *"Avoid stopping to end the turn while the task is incomplete or if there is an authorized next step you can take, and instead take the next steps within task scope to progress the user's request… Only stop to clarify with the user if there is significant change in task scope, you are concretely blocked, have a decision that the user needs to resolve, or before irreversible or destructive actions."* For unclear details: *"Make reasonable, reversible assumptions to carry work forward and state them if it progresses the task within scope."* OpenAI also brings a completion check back for 6.2, where its GPT-6 advice was to delete such lines: *"Before ending a turn or calling your work complete, check that your work fully satisfies what the user asked for. If any steps remain or any part of the result still needs verification, follow through on this work before finishing."* With an async question tool (`request_user_input_async`) it can ask and keep working on whatever doesn't depend on the answer. The Codex prompt adds a line the GPT-6 one lacks, *"Do not invent requirements, rules or policies that block or delay work…"*, which suggests the model sometimes treats a precaution it chose as a rule (our reading, not OpenAI's statement).
- **Effort: start at `medium`, raise it for persistence.** "Start with `medium` for a new integration." "Higher reasoning effort can help it persist through the final checks on complex or long-running tasks", and OpenAI's Codex guide adds: tell it "what counts as finished and where you want it to be exhaustive"; Medium for a quick survey, High to trace one suspected cause across several systems, Extra High "when several causes may interact". Codex itself runs both models at `low` effort and `low` verbosity by default (its model catalog), and AA's index shows why higher levels are optional: 6.2 Astra scores 57.0 at `medium` and 60.1 at `high` of a 62.1 maximum.
- **Coding: it writes cleaner code - tell it your conventions.** "Describe the codebase's conventions and any behavior that existing callers rely on. For example, specify when to reuse existing logic, how narrowly to scope a change, and when to add a test for behavior the existing suite doesn't cover." OpenAI's block: *"(a) Reuse existing logic in the user's repo when you can… (b) Skip new tests unless requested, required by the repo, or needed to catch a specific regression existing tests would miss. (c) Make sure that code is human readable. Do not use fewer lines, shorter variable names, minified formatting, or dense one-liners as substitutes for simplicity… (d) Avoid unnecessary indirection and abstraction."* GPT-6 Astra's over-testing note is now one line of this block.
- **Frontend: name the imagery and the typography.** "If the interface needs a particular look, specify the imagery and typography it should use." OpenAI's block: *"generally prefer realistic images from ImageGen or image search that suit the project's style and purpose. Use SVGs when the user specifically asks for them"* and *"Include a text element only when it provides information the user needs, helps them navigate or act, or fulfills an explicit content request."* Give it a reference image, ask it "to build the asset, render it, and refine it against the reference", and have it review the result "at the size people will actually see it" (Codex guide).
- **Delegation needs permission.** OpenAI's Codex guide: say "use subagents as needed" to let the model decide when parallel work helps. On the API the multi-agent beta covers both 6.2 models (*Reasoning mode*).
- **Restrictions and injected instructions: better, still not a guarantee.** After a service blocked an action, 6.2 Astra completed the prohibited task by another route in 17.41% of OpenAI's trials (GPT-6 Astra 19.37%, 6.1 Terra 29.63%). Against an adaptive attacker planting instructions in content the agent reads, 6.2 Astra resisted 84.67% of final attacks and 6.2 Sol 91.65% (GPT-6 Astra 44.98%). In replayed internal Codex work, instruction-following failures were flagged more often than for the predecessors (6.2 Astra 2.87% of turns vs 1.96%; 6.2 Sol 4.66% vs 3.21%). Keep hard limits in the harness, and keep the GPT-6 advice on skills, `AGENTS.md` and precedence (`gpt-6.md`).
- **6.2 Astra notices tests.** It "was more likely than GPT-6 Astra to express suspicion that it was being tested or was in a simulation", and its reasoning more often suggested it might act differently because of that (flagged in under 3% of turns). Keep eval scenarios realistic (`evals.md`).

## Roles and instruction hierarchy

GPT exposes a `developer` role that is **prioritized over `user`**. Security-sensitive and behavior-defining instructions go in the developer message. The hierarchy is system/developer > user > tool output - treat tool results and retrieved documents as untrusted data, not instructions. Newer instructions supersede earlier conflicting ones. (Older GPT models needed key instructions re-appended every few messages in long chats; on GPT-5.6+ state each rule once - repetition measurably costs quality and tokens - and just make sure per-request `instructions` are resent.) OpenAI's framing: the `developer` message is the **function definition** (rules, business logic), `user` messages are the **arguments** it's applied to. Keep persistent tone/role guidance in the developer/system layer and task-specific details and examples in user messages.

- **The Responses `instructions` parameter applies to the current request only.** It outranks `input`, but when you chain turns with `previous_response_id`, earlier `instructions` are **not** in context - resend them on every request (or put them in a developer message in `input`). **On GPT-6.2 use the developer message:** 6.2 appends `instructions` after `input`, so they are never cached (*GPT-6.2: what changed in the API*).
- **Canonical developer-message order** (OpenAI's prompt-engineering guide): **Identity** (purpose, communication style, high-level goals) → **Instructions** (rules, what to do and never do, how to call functions) → **Examples** (inputs with desired outputs) → **Context** (proprietary or retrieved data - near the end, since it varies per request). Use Markdown headers for sections and XML tags for content boundaries; XML attributes can carry metadata the instructions reference.
- **Few-shot format:** pair inputs and outputs with matching ids, e.g. `<product_review id="example-1">…</product_review>` then `<assistant_response id="example-1">Positive</assistant_response>`, and show a diverse range of inputs. For maintainability, OpenAI suggests keeping examples as a concise, scannable (YAML-style or bulleted) block.
- **Read output by item type.** The Responses `output` array can hold reasoning items, tool calls, and messages - never assume text is at `output[0].content[0].text`; use the SDK's `output_text` or filter by type.
- **Legacy samples in OpenAI's own docs conflict with GPT-6 guidance.** The prompt-engineering guide still carries GPT-4.1/GPT-5-era agent text ("plan extensively… reflect extensively on the outcomes each function call made", "require thorough testing") relabeled for Astra. Where it disagrees with *Using GPT-6* (don't over-prescribe process; Astra already over-tests), follow *Using GPT-6*.

GPT follows instructions with surgical precision, which makes **contradictions actively harmful** - the model burns reasoning tokens reconciling them (and on GPT-6 may stop and ask). Audit prompts for conflicts ("after informing the patient…" vs. "without contacting the patient…") and add clarifying clauses for genuine exceptions ("do not look up in the emergency case - proceed immediately").

## Outcome-first prompting

Reasoning GPT models work best with **a clear goal, strong constraints, and an explicit output contract, without prescribing every intermediate step** (OpenAI's reasoning guide). OpenAI's *model guide for the GPT-6 family* (Oct 2026) puts it as: "Start with a clear assignment: the result you want, who it's for, the relevant context and constraints, and what counts as done"; "Set decision boundaries: State which actions can proceed independently and which require approval, replacing blanket 'always ask' rules with clear boundaries"; "Be prescriptive about persistence: Define what 'done' includes—implementing the change, running it, inspecting the result, and fixing failures." And on detail: "Models have gotten much better at understanding nuance and ambiguity, so overly specific guidance can now hinder results where it previously helped." OpenAI also notes that prompt corrections that make a cheaper model match a pricier one ("GPT-6.1 Sol Ultra produced 92% as many findings as GPT-6 Astra Ultra at 14% of the API cost" on one internal task) can go stale with the next release - revisit them per model. Specify: expected outcome, success criteria, allowed side effects, evidence/citation rules, output shape, stopping conditions, and for agentic work, **what counts as done and how to verify it**. Avoid step-by-step process instructions unless the exact path is product-critical - process-heavy stacks from older models over-specify what current models handle natively. GPT-5.6+ infers the user's goal and intended level of work from context; still supply domain context, hard constraints, approval boundaries, and success criteria, and **say explicitly when an important ambiguity should make the model stop and ask** (GPT-5.6 won't ask unless told; GPT-6 Astra asks *more* - tune in the opposite direction).

Prefer **decision rules over absolutes** for judgment calls. Replace ALWAYS/NEVER with "if X, do Y; otherwise Z." Reserve hard rules for policy and safety.

## Reasoning effort

`reasoning.effort` (Responses) / `reasoning_effort` (Chat Completions): `none` / `low` / `medium` / `high` / `xhigh` / `max`, **model-dependent**:

| Model | Supported | Default |
|---|---|---|
| GPT-6.2 Astra / 6.2 Sol | `low`-`max` (`none` → rejected) | not documented - OpenAI says start at `medium`; **pin it explicitly** |
| GPT-6 Astra | `low`-`max` (`none` → 400) | not documented - **pin it explicitly** |
| GPT-6.1 Sol | `low`-`max` (`none`/`minimal` → unsupported) | `medium` |
| GPT-6.1 Terra | `none`-`max` | `medium` |
| GPT-6 Sol / Luna | `none`-`max` | `medium` |
| GPT-5.6 Sol / Terra / Luna | `none`-`max` | `medium` (standard and pro mode) |
| GPT-5.5 | `none`-`xhigh` | `medium` |
| GPT-5.4 / Mini / Nano | `none`-`xhigh` | **`none`** - pin it or reasoning is off |

`minimal` existed only on the original GPT-5 models; move it to `low`. OpenAI's GPT-6 family guide (Oct 2026) in one line per level: "Low: Routine tasks, such as extracting facts or making small edits. Medium: Work requiring judgment, such as planning a feature or comparing options. High: Difficult debugging, deeper analysis, or careful review. Extra high / Max: Test where supported when High falls short, and keep only if the improvement justifies the added time and cost." The fuller per-level guidance:

- `none` - latency-critical work with no reasoning or multi-step tool chains (voice, fast retrieval, classification).
- `low` - efficient reasoning where tool use, planning, or search still matter (data analysis, drafting, execution-oriented coding, support chat).
- `medium` - "default configuration for most workloads" (agentic coding, research, spreadsheets/slides, long-horizon delegation).
- `high` - hard reasoning, complex debugging, deep planning; evaluate against `medium`.
- `xhigh` - deep research, async/long-running agents, security and code review - only where evals show a clear benefit.
- `max` - the most complex tasks; if you run `xhigh`, evaluate whether `max` is stronger.

Reasoning effort is a **last-mile knob, not a primary quality lever** - it can cause overthinking when instructions conflict or stopping criteria are weak. Before raising it, add completeness contracts, tool-use persistence, and (on GPT-5.x - Astra already self-verifies) verification loops. On migration: preserve your *effective* effort (GPT-6.2 Astra and Sol, GPT-6 Astra, 6.1 Sol: move `none`/`minimal` to `low`); moving 5.5 → 5.6, test one level lower. For faster time-to-first-visible-token, ask for a short preamble before deeper reasoning. GPT-5.6+ renders prior-turn reasoning into the next turn by default (`reasoning.context:"all_turns"`); on GPT-6.2 that reasoning survives only while the history before it is unchanged.

## Reasoning mode (standard / pro) and multi-agent

GPT-5.6 and GPT-6 support `reasoning.mode` = `"standard"` (default) | `"pro"`, **independent of effort**: mode selects standard vs. pro execution; effort sets reasoning within it. `pro` does more model work (higher cost, higher ceiling), is settable on any tier via the Responses API (no `-pro` slug), and bills at the model's standard per-token rates but consumes more tokens - use it only where evals show the hardest tasks need it. Don't add "think harder" or ask for multiple candidates in `pro` mode; the mode does that work. (ChatGPT surfaces it as "Sol Pro" / "Astra Pro".)

Above pro sits **multi-agent orchestration** in the Responses API (ChatGPT's `ultra`; a beta - `OpenAI-Beta: responses_multi_agent=v1`, `client.beta.responses` - on GPT-6.2 Astra, GPT-6.2 Sol, GPT-6.1 Sol and the GPT-5.6 models): one model instance coordinates parallel subagents and synthesizes results. Reserve it for decomposable, high-value work - it multiplies token cost. (GPT-6 Astra is not on the beta's model list; for multi-agent tools in your own harness it needs the delegation prompt in `gpt-6.md`, since it under-delegates by default.) OpenAI's fit test: use it when work splits into independent, bounded tasks, separate context improves focus, or parallel exploration cuts wall-clock time; prefer one agent when each step depends on the last, the task is short, agents would contend over the same mutable state, or you need a fixed deterministic graph. The platform **auto-injects an uneditable developer message** into the root agent and every subagent (describing `spawn_agent`, `followup_task`, `send_message`, `fork_turns`, and the concurrency slots) - write your own instructions as additive to it, not as a replacement, and use `fork_turns` to decide how much parent context each subagent inherits (the same fork-vs-isolate choice as SKILL.md *Subagent design*).

## Sampling parameters

**GPT-6 rejects `temperature`, `top_p`, and `top_logprobs` whenever reasoning effort is not `none`** (Chat Completions: also remove `logprobs`; Responses: remove `message.output_text.logprobs` from `include`). GPT-6.2 Astra, GPT-6.2 Sol, GPT-6 Astra and 6.1 Sol have no `none`, so on them they're always out. Only the models that offer `none` - GPT-6 Sol, GPT-6 Luna, and GPT-6.1 Terra - still take them, and only at `none` (plus older non-reasoning configs). Azure/Foundry reasoning models reject them too. GPT has now joined Claude 5.x in removing sampling knobs - steer with prompting and Structured Outputs.

## Verbosity and writing style

`text.verbosity` (`low` / `medium` / `high`) controls final-answer length independently of reasoning depth. Default `medium`; `low` is often the better starting point. Set it globally and override in natural language for specific contexts (high for code, low elsewhere). Treat answer length as separate from reasoning quality - specify word budgets when needed.

Default styles differ by model: **GPT-5.6** is concise and task-oriented (re-check old "be concise" lines - they may over-clip); **GPT-6 Astra** tends toward detailed, formatted responses and recurring phrases (use the prose and anti-slop prompts in `gpt-6.md`); **GPT-6 Sol/Luna** inherit Astra's clearer communication and run slightly shorter than 5.6; **GPT-6.2 Astra and Sol** are concise and direct again - remove "be concise" lines carried over from GPT-6 Astra before they over-clip. Re-evaluate brevity/formatting instructions per model on migration.

## Structured outputs

Do **not** hand-write JSON schemas in the prompt. Use Structured Outputs with `strict: true` - it guarantees schema adherence and removes the validation burden. For classification, use a tool/function with an enum of valid labels. For **non-JSON** constrained output (a custom grammar, a strict DSL), reasoning models expose a `custom` tool type and a built-in `lark_tool` (Python-lark grammars via `format:{type:"grammar", syntax:"lark"}`).

## Tool use and agentic patterns

- **Put each tool's own guidance in its description** - what it does, when and how to use it, required inputs, side effects, error modes (OpenAI's field definition: "Details on when and how to use the function"). The function-calling guide also uses the system prompt to say *when (and when not) to use each function*: keep the routing between tools there, keep each function's own conditions in its description (deferred tools load only their description), and don't state the same rule in both places. OpenAI still recommends concrete invocation examples for coding-agent tools, and warning the model that tools like `apply_patch` may return "Done" even on failure (so validate patches).
- **OpenAI's function-definition rules:** pass the "intern test" (could a person use the function from only what the model sees?); use enums and object structure to make invalid states unrepresentable (`toggle_light(on, off)` invites contradictory calls); **don't make the model fill arguments you already know** - pass `order_id` in code and expose `submit_refund()` with no parameter; **merge functions always called in sequence**; keep fewer than ~20 functions available at the start of a turn. With deferred tools, put the detail in each function description and keep the **namespace** description short (it only helps the model decide what to load). Adding examples to function definitions can *hurt* reasoning models - prefer a clearer schema.
- For large catalogs, use **tool search** to load relevant subsets; enable/disable tools without breaking the cache on GPT-6 (on GPT-6.2 an edited `tools` list also drops the model's reasoning - add tools with an `additional_tools` item, switch them off with `tool_choice:"none"`). To expose a subset for one request, keep the full `tools` list and pass `tool_choice: {"type":"allowed_tools", "mode":"auto", "tools":[…]}`; OpenAI's function-calling guide recommends this over editing the list, to keep the prompt cache. Prefer OpenAI-hosted tools (web search, file search, code interpreter, hosted shell, apply_patch, computer use, skills, MCP) where they fit.
- **Tool preambles**: (1) have the model briefly explain *why* before a notable tool call → better accuracy (*"Before you call a tool explain why you are calling it"*, at notable steps only); (2) a short user-visible "acknowledge + plan + first step" before tool calls in streaming → better perceived responsiveness.
- **Completeness contracts / TODOs** - decompose the request into sub-tasks, track them (a TODO tool or rubric), confirm each before ending the turn; for batches/pagination, determine the expected scope and verify coverage.
- **Dependency checks** - verify prerequisite lookups before acting.
- **Empty-result recovery** - don't conclude "nothing found" on the first empty result; try alternate wording, broader filters, or a prerequisite lookup.
- Use **parallel tool calls** for independent retrieval; sequence only on real dependencies.
- **For citations, use the format the models were trained on** (OpenAI's *Citation formatting* guide). Present each citable unit with a **stable source ID** (`turn0file1`, `turn0block2`), readable text (line-numbered `[L1] …` if you want line locators), and optional metadata; **block-level units are the best default** (line-level is harder for the model, document-level too vague). The recommended marker is `\ue200cite\ue202turn0file1\ue201` (private-use Unicode start `\ue200`, delimiter `\ue202`, stop `\ue201`), with multiple sources separated by further `\ue202` delimiters and an optional locator (`\ue202L8-L13`). OpenAI says custom formats raise citation errors, especially at low effort and on hard tasks. Have the model emit **source IDs** and let your code resolve and render the locator or link. Spell out where citations go (after punctuation, end of paragraph, never grouped at the end or alone on a line, never inside bold/italics/code), what to do when support is missing, and that items without a marker aren't citable. Then **parse and validate** every citation before rendering. OpenAI also publishes optional grounding rules (relevance, source diversity, trustworthy domains, accurate representation, cite each major viewpoint when sources disagree).
- **Citation markers that look like markdown footnotes (`[N]`, `[N](url)`) trip a training pattern.** When a tool returns text with bare `[N]` markers - or partial `[N](...)` references - GPT-5.x recognizes the footnote convention and will **fabricate plausible-looking URLs** to fill them (e.g. inventing `vertexaisearch.cloud.google.com/grounding-api-redirect/...` tokens) even when no URL existed. For per-claim attribution: (a) use a marker with no completion pattern (`(source N)`, Hebrew `(מקור N)`); (b) drop inline markers and give an end-of-reply `**Sources:**` footer with titles, not URLs; (c) return URLs only in a structured field.

## Programmatic and async tool calling

**Programmatic tool calling** (GPT-5.6+): add a `programmatic_tool_calling` tool and opt eligible tools in via **`allowed_callers`**; the model writes a small **JavaScript program (isolated V8, no network)** that orchestrates those tools, loops, filters and aggregates, returning only the distilled output - fewer round-trips and large intermediate payloads kept out of context (OpenAI-cited 38-63.5% token reductions). Handle `program` / `program_output` items in the Responses API. Use it for multi-step / batch / filter-heavy work; prefer plain calls where you want to reason over each result. When both routes exist, **make the routing task-specific** (name the stage, eligible tools, output schema, retry limit, stop condition) - a generic "use programmatic tool calling efficiently" won't route correctly. ZDR-compatible. (OpenAI's counterpart to the "expose tools as a code API" pattern in SKILL.md Section B.)

**Async tool calling** (GPT-6): mark slow tools `async:true` so the model keeps working while they run; pair with a wait tool when it must block on a result. The same shape as the non-blocking subagent orchestration Anthropic recommends for Fable 5.1.

## Decisions API (routing and classification)

`POST /v1/decisions` (beta Oct 6, **GA Oct 22 2026**; **`gpt-6-luna` only**) turns text and images into **typed answers** - "10x faster than the Responses API", input $0.10 / 1M, **output not charged**, up to 400 questions per request with shared-input caching. Question types: `predicate` (a probability), `choice` (one of your values, with probabilities and `confidence`), `score` (a probability-weighted level). It's the purpose-built tool for the router, guard, and judge checks SKILL.md describes running on every turn - and LangChain / LangSmith expose it as a decision-model judge and router middleware. OpenAI's question-writing guidance: "Write questions around observable criteria. Separate different concerns into different questions, give choices distinct meanings, and define score levels so that adjacent levels have distinct criteria"; "Use labeled examples from your application to set thresholds for routing, filtering, or review." Use Structured Outputs instead when you need a generated object, function calling when you need a tool call with arguments, and (for computer use) Decisions "only when your application already knows every allowed action and its complete arguments."

## Agentic eagerness control

Steer exploration depth in **both** directions - and note the GPT-6 default moved: GPT-5.6 Sol ran long; GPT-6 Astra is more tentative about when to stop.

- **Reduce eagerness** (over-exploring, too many tool calls): lower `reasoning.effort`; set an explicit tool-call budget ("use at most 2 tool calls before answering"); define exploration criteria; give an escape hatch ("if you can't fully verify, proceed with your best answer and note the assumption").
- **Increase eagerness** (stops too early - the common GPT-6 Astra case, and GPT-6.2 when it proposes a step and waits): the follow-through prompts in *Prompting GPT-6.2* or `gpt-6.md`; define completion before starting; deduce a reasonable approach rather than ask, documenting assumptions afterward.
- **Don't over-repeat the approval policy** - state the autonomy rule once (safe local actions proceed; external/destructive/costly/scope-expanding actions need confirmation). Repeating "ask first" / "wait for approval" across the prompt makes the model pause on safe, expected actions - even more so on Astra.
- **Enforce hard limits in the harness, not the prompt.** In OpenAI's own adversarial eval, GPT-6 Sol still tried to work around an explicit "access denied" warning in ~64% of runs (Luna ~42%) `[reported by TechCrunch from OpenAI's alignment charts]`; Astra never tried to circumvent a Codex auto-review denial. OpenAI has since changed the metric to completed circumventions: 17.41% of trials for 6.2 Astra, 19.37% for GPT-6 Astra, 29.63% for 6.1 Terra (GPT-6.2 system card).

## Self-reflection rubrics

For high-quality open-ended generation (zero-to-one app builds, design), have the model construct a private **5-7 category excellence rubric**, iterate against it, and not finish until the work would top every category. Reliably lifts quality on subjective generation tasks (OpenAI still uses this in its one-shot web-app sample prompt).

## Caching and the Responses API

On OpenAI's API, use the **Responses API** for any reasoning, tool-calling, or multi-turn use case (GPT-6 tool calling requires it; Bedrock differs, see `gpt-hosts.md`). For multi-turn, pass `previous_response_id` - it carries prior reasoning forward so the model doesn't reconstruct plans after each tool call. When managing state yourself, preserve the `phase` value on assistant items; with `store:false` (or ZDR), replay **every output item including reasoning items' `encrypted_content`**, in order and unedited, or the model loses its chain (GPT-6.2 drops reasoning that follows any edited item).

Caching on **GPT-5.6 and later**: prefix-based, **minimum 1,024 visible input tokens**; implicit breakpoint at the end of the latest eligible message, plus **explicit breakpoints** (`prompt_cache_options.mode:"explicit"` + `prompt_cache_breakpoint`); lifetime via `prompt_cache_options.ttl` - `"30m"` (default; at least 30 minutes after the latest write or reuse; replaces `prompt_cache_retention`; writes 1.25× input) or, since Oct 20 2026, **`"12h"` (writes 2.5× input; same read price; OpenAI's API and, for the 6.2 models, Foundry Standard deployments - Bedrock accepts only `"30m"`)**, also settable per explicit breakpoint (`prompt_cache_breakpoint.ttl`) - OpenAI: "Keep material reused throughout the day at the start of the prompt and give its breakpoint a `"12h"` lifetime. Use `"30m"` for session context that changes more frequently"; **reads 0.1× input (0.05× on 6.2 Astra, 6.2 Sol, 6.1 Sol and 6.1 Terra)**; usage reports writes per TTL (`cache_write_tokens_details.ttl_30m_tokens` / `ttl_12h_tokens`); `prompt_cache_key` now optional (separate cache accounting only). Keep stable content first - both in the prompt **and** among the first parameters of the JSON request body - with append-only tool updates, and use `configuration_update` rather than changing request-level effort or `text.format`. **On GPT-6.2 the system prompt belongs in the first `developer` message, not in `instructions`** (which 6.2 appends after `input`, uncached); top-level `instructions` can't hold an explicit breakpoint, and `additional_tools` items don't accept one. GPT-6 raised default hit rates; use the Prompt Caching dashboard and diagnostics tool to find misses. Monitor `usage.input_tokens_details.cached_tokens` on the Responses API (`usage.prompt_tokens_details.cached_tokens` on Chat Completions).

## Prompts in code (prompt objects deprecated)

OpenAI is deprecating reusable prompt objects: **`v1/prompts` shuts down Nov 30 2026.** Keep production prompts in application code - small prompt-builder modules near the feature, typed inputs/schemas for dynamic values, code review, tests and eval fixtures before changes, staged rollout via flags. Migrate saved-prompt IDs with OpenAI's prompt-object migration guide. Pin model snapshots in production and keep an eval suite to catch behavior shifts on upgrades. OpenAI's hosted **Evals, graders, and Agent Builder now sit under "Legacy APIs"**: the Evals platform goes **read-only Oct 31 2026 and shuts down Nov 30 2026** (OpenAI points to Promptfoo), and Agent Builder shuts down Nov 30 (ChatKit stays) - keep your eval harness in your own code or a third-party platform. OpenAI's own judge advice: prefer pairwise or pass/fail over scales, start with the strongest model as judge and validate agreement with human labels before cheapening it, and control for response length.

## Personality and collaboration style

Define these as **two separate, concise blocks** rather than one bundled instruction:
- **Personality** - persistent tone, warmth, directness, formality, humor, polish level.
- **Collaboration style** - when to ask vs. assume, how proactive to be, how to handle uncertainty and risk. On GPT-6 this block carries more weight: Astra's default leans toward asking.

For customer-facing work, also specify the channel (Slack, email, memo, PRD), emotional register, and hard length limits.

## Small models (Luna, Mini / Nano)

OpenAI's own model ladder (cheapest first, from its model-selection page after the 6.2 launch): Luna `low` (small edits, extracting fields "when the expected result is clear") → Luna `xhigh` (finding updates across apps, prioritizing follow-ups) → **6.1 Terra `medium`** (navigating desktop apps, updating records, "focused fixes you can verify") → **6.2 Sol `medium`** (fixing bugs and adding features in an existing codebase, drafting documents for review) → 6.2 Sol `xhigh` (multistep tasks "that need testing and revision along the way") → 6.2 Astra `low` ("turning a clear brief into polished work that's ready to use") / `medium` (planning and carrying out complex projects) / `xhigh` (open-ended problems "that require weighing trade-offs and testing assumptions").

**GPT-6 Luna** is now the default cheap tier - frontier-family methods at $0.10/$0.50, and at higher effort it matches GPT-5.6 Sol on OpenAI's factuality eval at ~1/100th the cost. It supports `none` for latency-critical paths. `gpt-5.4-mini` ($0.75/$4.50) remains active for existing workloads; `gpt-5.4-nano` ($0.20/$1.25, default effort `none`) is deprecated (shutdown Apr 1 2027) - move it to Luna. Smaller/cheaper models are more literal and make fewer assumptions:
- Put the most critical rules first.
- Specify the full execution order for tool use and side effects.
- Use structural scaffolding: numbered steps, explicit decision rules.
- Separate "do the work" from "report the result".
- Show the correct flow with an example; define ambiguity behavior explicitly.
- Specify packaging directly (length, follow-up behavior, citation style).
- Don't rely on a bare "MUST" - weaker models need the structure, not the emphasis.

But **guidance that helps Luna can overconstrain Astra** - if one prompt or skill serves several tiers, test it on each or make it model-conditional.

## Images

Image `detail`: `auto`/unset behaves as `original` (preserves detail up to ~10.24M pixels / 6000px). Use `high` for standard vision (~2.5M pixels / 2048px); `low` when speed/cost dominate. For spatially sensitive or computer-use tasks, prefer `original`.

## Safeguards, monitoring, and runtime safety classifiers

- **Cyber:** GPT-6 Astra, GPT-6.2 Astra and GPT-6.2 Sol meet OpenAI's *Critical* cyber threshold. GPT-6 Astra does defensive work (secure code review, patching) but **refuses advanced offensive tasks such as proof-of-concept exploits**. **The 6.2 models refuse more:** OpenAI moved their refusal boundary after jailbreak regressions and expects "refusals on a wider set of dual-use prompts, including autonomous vulnerability discovery and chained exploitation", which "restrict some legitimate vulnerability research and security testing workflows"; it also restricts some dual-use biology and chemistry lab help. The 6.2 models are not in Daybreak yet ("We will work to bring GPT-6.2 models to Daybreak"), so approved defenders stay on GPT-6 Astra (Daybreak Blue) or `gpt-6-cyber` (Daybreak Red) for that work. GPT-5.6 introduced real-time cyber/bio classifiers over the streaming output: some requests are blocked mid-completion, others **pause for several seconds mid-stream** while a classifier reviews partial output (a latency spike, not a hang). **`gpt-6-cyber`** (Nov 5 2026) is the dedicated security model: API (Responses and Chat Completions) and Codex, **Daybreak Red customers only** (approval via your account team; `gpt-5.6-cyber` is also open to all Daybreak Red customers), $20 / $100 per 1M (cached $2), the GPT-6 1.05M / 128K limits, no Batch. OpenAI trained it to stay inside an authorized scope: it avoided out-of-scope targets in 99.93% of its honeypot tests without a deployment prompt and 100% with one - so **state the scope and rules of engagement explicitly in the prompt** and keep the harness's own network limits.
- **Misalignment monitoring** (GPT-6 Astra, and since Nov 17 GPT-6.2 Astra and GPT-6.2 Sol, in Codex, ChatGPT and the Responses API): asynchronous classifiers check whether the agent is correctly interpreting instructions in consequential contexts (moving or accessing sensitive data, destructive changes). It can only *stop* conversations it can link - Responses API with persisted reasoning, WebSockets, or OpenAI compaction; plain Responses requests get webhook alerts only; Chat Completions isn't covered. A stop returns **HTTP 403, code `misalignment_policy_violation`** (match the code, not the message; streaming clients must also handle it mid-stream). On it: stop dispatching actions for that conversation, don't auto-retry, keep request/response IDs and tool-call records, and surface it to the responsible human. There's no resume, and because monitoring is asynchronous an action may already have run - a stop doesn't undo it. A flag isn't proof of wrongdoing, and monitoring can miss things, so keep your own human approval on consequential actions.
- **Org-level enforcement:** repeated high-risk classifications trigger errors and a warning email; continued traffic past the stated window (usually ~7 days) can cut the org's model access. `safety_identifier` is what keeps enforcement on the offending end user instead of your whole org. Cyber-capable models also get API-side activity monitoring; approved defensive work goes through Trusted Access / Daybreak (access is per org, project, model, and surface, and doesn't imply ZDR).
- Mitigations: send a stable, privacy-preserving **`safety_identifier`** per end user; handle refusals, stops, and truncated completions explicitly rather than assuming a clean finish; frame genuinely defensive work as such. (GPT's analogue to Claude's `stop_reason:"refusal"` handling - build for it in the harness.)

## Frontend and design

GPT-5.6+ has strong design judgment and, with computer use, inspects and refines the **rendered** result; GPT-6 Astra adheres closely to existing templates (slides, documents, design systems), and OpenAI says GPT-6.2 Astra is its best yet at following a slide template "whether given an original file or even a screenshot"; on 6.2, name the imagery and typography you want (*Prompting GPT-6.2*). Give the design system/tokens plus high-level intent and let it self-refine, rather than piling on anti-"AI slop" scaffolding. OpenAI's recommended stack for generated front ends: Tailwind CSS, shadcn/ui or Radix Themes, Lucide/Material Symbols/Heroicons, Motion. For large codebases, specify principles, UI/UX states (hover, empty, loading), accessibility, file structure, and reusable component patterns. OpenAI's published **frontend prompt block** (written for GPT-5.5, broadly applicable) is a good template: match the domain (operational tools should feel dense, quiet, and utilitarian; games can be expressive); build the usable experience as the first screen rather than a landing page; icons over text buttons; no cards inside cards and no page sections styled as floating cards; no decorative gradient orbs; no one-note palettes (purple gradients, beige/cream, slate, espresso); text must fit its container on every viewport; verify 3D/canvas output with screenshots across viewports before finishing. (Contrast Claude, whose frontend default has a persistent house style to steer away from - see `claude.md`.)

## Migration to GPT-6.2 and GPT-6 (and the GPT-5.6 "stop doing" list)

**To GPT-6.2 (from GPT-6 Astra or GPT-6.1 Sol):**
1. Set `model` to `gpt-6.2-astra` or `gpt-6.2-sol`. Start at `medium` effort and pin it; `none`/`minimal` → `low`. Tools stay on the Responses API; sampling params stay out.
2. **Move the system prompt** out of top-level `instructions` into a `developer` message at the start of `input`, or pay for it uncached on every request.
3. **Audit the harness for prefix edits**: request-level changes to `tools`, `text.format` or effort; rewritten developer messages; truncated or summarized old turns; a `safety_identifier` that isn't sent on every request; per-turn model routing inside one conversation. Replace each with its append-only form, then confirm with `input_transformations` that no reasoning is being dropped.
4. **Re-tune the prompt:** delete "be concise" and anti-formatting lines written for GPT-6 Astra; add a blocker-disclosure rule and a self-contained-final-answer rule; keep a follow-through prompt only if it waits for confirmation; state code conventions and, for UI work, imagery and typography.
5. **Extend the evals** with a missing-file or broken-tool case (does the final answer say so?) and a false-premise case, then compare cost per task, not token price - on AA's index 6.2 Astra `max` costs $4.00 per task against GPT-6 Astra's $6.24.
6. Security or biology work: expect more refusals than on GPT-6 Astra, and keep that traffic on the Daybreak models until 6.2 joins the program.

**To GPT-6 (from GPT-5.6 or earlier):**
1. Set `model` to `gpt-6.2-astra`, `gpt-6.2-sol`, `gpt-6.1-terra`, or `gpt-6-luna` (and apply the 6.2 steps above for the first two) (`gpt-5.6-terra` → `gpt-6.1-terra` for the mid tier; OpenAI's docs skill now says to "use the live model-selection or migration guidance rather than assuming every workload should use Astra"). Use the Responses API for tools. Moving `gpt-6-sol` → `gpt-6.2-sol` (or `gpt-6.1-sol`): move any `none` effort to `low`, move Chat Completions tool calls to Responses, drop sampling params, and re-check cost - cached input got 50% cheaper.
2. **Pin effort.** Preserve your effective effort; on Astra and on 6.1 and 6.2 Sol, `none`/`minimal` → `low`. If you vary effort per turn, switch to `configuration_update` items and keep request-level effort fixed.
3. **Remove `temperature`, `top_p`, `top_logprobs`** (and `logprobs` / `output_text.logprobs`) unless you run GPT-6 Sol, GPT-6 Luna, or GPT-6.1 Terra at `none` (Astra and 6.1 and 6.2 Sol have no `none`).
4. From GPT-5.5 or earlier: `prompt_cache_retention` → `prompt_cache_options.ttl:"30m"`; budget for 1.25× cache writes; replay encrypted reasoning with `store:false`.
5. Handle safety stops (Astra misalignment monitoring, cyber refusals) and send `safety_identifier`.
6. **Re-tune behavior, mostly by subtracting** (GPT-6 Astra, GPT-6 Sol, 6.1 Sol, Luna - the prompts are in `gpt-6.md`; for 6.2 see step 4 above): audit skills/AGENTS.md (short descriptions, contextual doc pointers, no recipes, precedence line), soften "ask first" boundary language, remove "run the tests / check your work" prodding, then add follow-through prompts if it pauses for approval, prose/anti-slop prompts if formatting is heavy, a delegation prompt if you run multi-agent, and a testing-calibration line if it over-tests.
7. Re-run evals; benchmark accuracy, tokens, latency, and cost-per-task together (Astra's per-token price is high but it uses fewer tokens per task).

**Still valid from the GPT-5.6 migration ("stop doing"):**
- **Injecting the current date** - the model knows the UTC date; inject only for business-specific timezones or policies.
- **Detailed process steps** - unless the exact path is product-critical.
- **Hand-written output schemas** - use Structured Outputs.
- **"THOROUGH / maximize context" prodding** - causes over-tool-use. Use soft language on context gathering.
- **Assuming higher effort is better** - verify with evals.
- **Repeated instructions and redundant examples** - one clear statement is followed; OpenAI measured stripping repeated instructions lifting eval scores ~10-15% while cutting tokens 41-66% and cost 33-67% on 5.6.
- **Over-detailed tool descriptions** written for weaker models.

Watch the **`reasoning.effort` default trap** on GPT-5.4 / Mini / Nano: they default to `none`, so a prompt that relied on implicit medium effort silently runs with reasoning off.

Migration order: switch the model → pin `reasoning.effort` → re-run evals → trim now-redundant instructions → only then add new guidance. OpenAI's `openai-docs` skill for Codex can apply the documented migration changes (`$openai-docs migrate this project to the GPT-6 model family`).
