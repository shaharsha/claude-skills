## Findings

### 1. File output buffers the entire unbounded object in memory

`api/services/vault/raw_read.py:310-319` · **high** · performance · confidence 0.99

**Evidence.** The ceiling is bypassed when `to_file` is true: `elif not to_file and size and size > DEFAULT_MAX_BYTES`, but the implementation still performs `body = vaultclient.s3().get_object(**kwargs)["Body"].read()`. The CLI writes that byte string only after the full read returns.

**Failure scenario.** An analyst uses `raw fetch -o export.csv` on a valid sealed export larger than the process's available memory. The nominal file-output remedy disables the ceiling, then allocates the entire object in RAM; the process is killed or raises MemoryError before the output file is written. The new test uses the small `ORIGINAL` fixture, so it still passes despite this failure mechanism.

**Suggested fix.** Give the file path or a binary sink to a dedicated pinned download function and copy the S3 StreamingBody to a temporary file in bounded chunks, then atomically rename it. Keep the in-memory ceiling for callers that request returned bytes.

### 2. The parser accepts both mutually exclusive output modes

`scripts/torque_admin.py:819-822` · **medium** · api-contract · confidence 0.99

**Evidence.** `-o/--out` and `--stdout` are registered as two independent arguments, despite the documented syntax `(-o out.csv | --stdout)`. The handler later gives `args.out` precedence.

**Failure scenario.** `torque-admin raw fetch ... -o result.csv --stdout` parses successfully. Although the analyst explicitly requested bytes on stdout, the command writes bytes only to the file and emits JSON provenance on stdout, which can silently feed the wrong data into a pipeline.

**Suggested fix.** Put `-o/--out` and `--stdout` in an argparse mutually exclusive group with `required=True`; remove the redundant manual at-least-one check.

### 3. Timestamp ambiguity is ignored after unreadable rows are filtered

`api/services/vault/raw_read.py:200-267` · **medium** · correctness · confidence 0.98

**Evidence.** Newest/tie resolution is computed only over `verified`: `newest = max(... for c in verified)`. Later, incomplete rows are surfaced only when their timestamp is strictly greater: `if ... > ... and c["session_state"] != "sealed"`.

**Failure scenario.** A sealed verified copy and a later-created failed mismatch for the same path are both recorded within the same second. The failed row is removed before tie detection and is not `>` the chosen timestamp, so resolve returns the sealed bytes with `newer_incomplete_runs: []`, even though the record cannot determine whether the failed attempt was newer. Separately, if two sealed fallback runs share a timestamp and a newer verified-but-failed run triggers the refusal, `max(complete, key=started_at)` arbitrarily recommends one UUID-ordered fallback as `the newest COMPLETE run`.

**Suggested fix.** Apply the same-second ambiguity rule across all path candidates before filtering. Surface or refuse unreadable candidates whose timestamp equals the chosen timestamp, and detect ties before recommending a complete fallback.

### 4. Explicit-run provenance falsely reports no other runs

`api/services/vault/raw_read.py:149-251` · **medium** · correctness · confidence 0.98

**Evidence.** Candidates are obtained with `list_objects(conn, slug, run_id)`, which scopes the query to the named run. `other_runs` is then derived only from that scoped list: `[c["run_id"] for c in verified if c["run_id"] != chosen["run_id"]]`.

**Failure scenario.** Runs A and B both contain verified `revenue.csv`. Calling `raw fetch --run A` returns `other_runs: []` because B was excluded from the query, contradicting the field and docstring claim that the other runs are listed. A provenance consumer can therefore conclude the named path has no alternative recorded copies.

**Suggested fix.** Use the run-scoped candidates only to choose the requested record, then query all client candidates for the `other_runs` annotation; alternatively omit `other_runs` on explicit-run reads so an empty list does not make a false claim.

### 5. Unreadable refusal calls a verified row “never verified”

`api/services/vault/raw_read.py:158-191` · **medium** · error-handling · confidence 0.97

**Evidence.** A row is readable only with both `state == "verified" and version_id`, but `_why` has branches only for `mismatch` and `missing`; every other combination reports `never verified ... a VersionId is captured at SEAL time`.

**Failure scenario.** S3 HEAD returns matching size/checksum but no VersionId. sessions._verify_object records `state='verified', version_id=NULL`, and because seal checks only the state, the session can become sealed. raw fetch safely refuses it, but reports that it was never verified and recommends replacing the drop. A mismatch row with a null VersionId is likewise told `its VersionId exists`.

**Suggested fix.** Partition object state and VersionId independently. Give `verified` plus missing VersionId its own message explaining that verification succeeded but no immutable pin was recorded; condition the mismatch wording on whether a VersionId actually exists.

### 6. The state-space test cannot prove the writer set is closed

`tests/test_vault_raw_read.py:678-711` · **low** · test-gap · confidence 0.99

**Evidence.** States are derived only with `re.findall(r"UPDATE upload_sessions SET state = '(\w+)'", sessions_src)`, while writer discovery looks only for the exact case- and whitespace-sensitive substring `UPDATE upload_sessions SET state` in Python files.

**Failure scenario.** A future change in sessions.py inserts a session with explicit state `quarantined`, or writes it using `UPDATE upload_sessions\nSET state = ?`. The new state becomes reachable, but neither regex sees it; the writer filename remains sessions.py and every assertion in the purported closure test still passes.

**Suggested fix.** Enforce the state domain with a database CHECK constraint and test that an unknown state is rejected. Do not use source-string enumeration as proof that the database state space is closed.
