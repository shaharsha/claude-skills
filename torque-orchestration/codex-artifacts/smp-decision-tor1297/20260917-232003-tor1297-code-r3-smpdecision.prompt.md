<intent>
GOAL. An authored HTML page carries a one-line as-of date ("Data through July
2026"). `refuse_edge_beyond_rendered` in `authored_pages/_recipe/as_of.py`
refuses to build a page whose declared date disagrees with the periods the
page's own figures draw. A forecast page draws past its data edge by
construction, so forward-looking traces must be excluded from that comparison.
Before this change they were excluded by matching the trace's NAME against a
regex. This change replaces that with a marker the BUILDER sets, and adds a
verdict for the case where the exclusion empties the period set.

REQUIREMENTS AND INVARIANTS the change must satisfy:
 1. The discriminator may not be a reader-facing string. It must be positive
    (a trace is excluded only if it declares itself), structural, per TRACE
    (never per figure or per page), and invisible to a reader of the page.
 2. Renaming a trace must not move any verdict.
 3. The exclusion must never produce the `no-period-axis` verdict. That verdict
    means "this page draws no dated axis at all" and is publishable; a page
    whose dated series were all excluded is a different fact.
 4. When the exclusion empties a non-empty period set the verdict is
    `all-projection`, and it may publish ONLY IF every marked trace's latest
    period is strictly LATER than the declared edge. A marked trace that stops
    at or before the edge must refuse and be named.
 5. An UNMARKED forward-looking trace must be COUNTED (so the page refuses),
    never silently excluded.
 6. A record written under the old name rule must be refused by the renderer,
    which holds no figure specs and cannot re-derive the period set.

RUNTIME CONTEXT. `as_of.py` runs once per page build, single-threaded, in the
build process, before anything is written. It is loaded STANDALONE by
`build_lib.sh` via `spec_from_file_location`, so it deliberately imports nothing
from `api/`. Its inputs are the page's own builder output (trusted, in-process)
— not user input. A refusal aborts the build and writes nothing. The pages it
gates are a real client's investment-decision pages and are IMMUTABLE once
published, so a false PASS is far more expensive than a false REFUSE.
`rendered_check_problem` is the second door: it runs at render time in
`scripts/build_page.py`, reads only the recorded JSON, and has no database and
no figure specs.
