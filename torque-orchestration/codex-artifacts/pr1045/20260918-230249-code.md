## Findings

### 1. `tenant create` is not a valid torque-admin command

`docs/prompts/smp_red_team_prompt.md:251-255` · **medium** · api-contract · confidence 1

**Evidence.** The new instruction says ``torque-admin tenant create` writes it into the `clients` registry`, but `scripts/torque_admin.py` defines tenant subcommands `add`, `list`, and `update`; there is no `tenant create`.

**Failure scenario.** An agent follows this active prompt while registering a red-team client. argparse rejects `create` as an invalid tenant subcommand, so the client is never registered and the picker step cannot complete.

**Suggested fix.** Replace `tenant create` with the actual `torque-admin tenant add` invocation and show the required `--name`, `--key`, and relevant product/simulation flags.

### 2. One-shot test allows a weaker data-state guard to pass

`tests/test_canary_backfill.py:164-186` · **medium** · test-gap · confidence 0.99

**Evidence.** The test promotes only `silver_canary`, then explicitly leaves `browser_drill_co` and `tor682_canary` at 0: `assert after["browser_drill_co"] == 0 and after["tor682_canary"] == 0`.

**Failure scenario.** A weaker migration guarded by “skip whenever any named canary is already 0” passes every test: after the first run two untouched rows remain 0, so the tested single promotion survives. If an operator promotes all three canaries, however, the next boot sees no zero sentinel and demotes all three again.

**Suggested fix.** Promote all three rows before the repeated boots and assert all remain 1. Also assert that the column comment exists after the first migration, independently of row values.

### 3. Concurrent first boots can overwrite an operator promotion

`db/schema.py:2894-2905` · **medium** · concurrency · confidence 0.94

**Evidence.** `IF NOT EXISTS (...) THEN UPDATE clients SET is_real = 0 ...; COMMENT ON COLUMN ...; END IF;` checks for the absent marker without serializing competing first executions.

**Failure scenario.** Two new containers start concurrently on the first rollout and both observe no comment. The first commits the backfill and marker; an operator then runs the supported promotion; the second already-admitted DO block resumes and writes the promoted row back to 0 before committing. Thus the marker prevents later sequential boots but not an overlapping first boot.

**Suggested fix.** Acquire a transaction-scoped advisory lock at the start of the DO block, before checking pg_description, then recheck the marker while holding it. This serializes only this migration and does not lock the served clients table on no-op boots.

### 4. Migration comment cites the wrong writer and CLI syntax

`db/schema.py:2870-2890` · **low** · maintainability · confidence 1

**Evidence.** The comment names ``torque-admin tenant update <slug> --real`` and then states ``api/services/vault/clients.py` is the only production writer of this column.` The parser requires `tenant update --slug <slug> --real`, and `api/services/control_plane/tenants.py` performs the production UPDATE of `is_real`.

**Failure scenario.** An operator copies the documented command and argparse rejects the positional slug. Separately, a maintainer auditing the claimed sole writer inspects the vault INSERT path but misses the supported update path that owns later operator decisions.

**Suggested fix.** Use `torque-admin tenant update --slug <slug> --real` and cite `api/services/vault/clients.py` for insertion plus `api/services/control_plane/tenants.py` for updates.

### 5. Workbook source map omits product-specific slots

`scripts/page_status_workbook.py:15` · **low** · correctness · confidence 0.99

**Evidence.** The new map says `Product/Slot   clients (is_real) x companies._SLOTS`, while `build()` calls `served_slots(code)`, which returns `_SLOTS` plus matching `_PRODUCT_SLOTS`.

**Failure scenario.** A reader follows the new source map to reproduce or audit the workbook population. For a product such as ALM with product-specific Deal Ops slots, the documented cross-product omits rows that the workbook actually emits.

**Suggested fix.** Describe the source as real routable `client_registry.tenants()` crossed with `served_slots(code)`, explicitly including matching `_PRODUCT_SLOTS`.

### 6. Atomic UPDATE/marker requirement is not tested

`tests/test_canary_backfill.py:108-217` · **low** · test-gap · confidence 0.96

**Evidence.** Every test exercises successful `init_db()` calls and resulting rows; none checks that UPDATE and COMMENT remain in one migration statement or forces a failure after UPDATE.

**Failure scenario.** A future refactor splits the guarded UPDATE and COMMENT into successive `_PG_MIGRATIONS` entries. All current tests remain green. If COMMENT is then cancelled by a lock timeout on first boot, autocommit has already committed the UPDATE without its marker, rearming the migration.

**Suggested fix.** Add a structural assertion that the named UPDATE and COMMENT occur in the same single DO migration entry, or an integration control that proves a post-UPDATE exception rolls back both effects.
