## Findings

### 1. The red-team prompt names a nonexistent tenant subcommand

`docs/prompts/smp_red_team_prompt.md:251-255` · **high** · api-contract · confidence 1

**Evidence.** The new instruction says: ``torque-admin tenant create``. At this revision, scripts/torque_admin.py defines tenant subcommands `add`, `list`, and `update`; only the separate `client` group has `create`.

**Failure scenario.** A worker follows the prompt to register SMPRT and runs `torque-admin tenant create ...`; argparse rejects the command, so the prescribed registration workflow cannot be completed.

**Suggested fix.** Document `torque-admin tenant add --key ... --name ... [--slug ...] [--product-code ...] [--order ...] [--simulated]`.

### 2. An active plan still recommends deriving demos from the dead literal

`docs/superpowers/plans/2026-08-29-slot-review-surface.md:2315-2319` · **high** · spec-violation · confidence 1

**Evidence.** Outside the code fences, the plan still says: `Its demo set is DERIVED (_REGISTRY product codes minus _REAL_PRODUCTS)` and `Prefer this to the _DEMO_CODES literal above if that pin holds at build time; verify it.`

**Failure scenario.** An agent following this implementation plan recreates the subtraction using the current database-backed real set. On an empty database or failed registry read, every registered product becomes a demo, silently labelling real-client products simulated. The cited `_REAL_PRODUCTS` equality pin no longer exists to prevent it.

**Suggested fix.** Strike this recommendation and state that the shipped `_DEMO_CODES` declaration is intentional; keep the historical text clearly marked as rejected.

### 3. The one-shot test accepts a row-state sentinel as its guard

`tests/test_canary_backfill.py:164-186` · **medium** · test-gap · confidence 0.99

**Evidence.** The test promotes only `silver_canary`, then explicitly requires the other two rows to remain 0: `assert after["browser_drill_co"] == 0 and after["tor682_canary"] == 0`. It never asserts that the pg_description marker exists.

**Failure scenario.** Replace the comment guard with `IF no named canary currently has is_real = 0`. Every test passes: the first run applies, and after the test promotes one row the other two zero rows suppress later runs. In production, promoting all three removes that sentinel, and the next boot demotes all three again.

**Suggested fix.** Assert the marker exists after the first boot, and promote all three canaries before subsequent boots so no row value can act as the one-shot marker.

### 4. A required falsifier still depends on the deleted symbol

`docs/superpowers/plans/2026-08-31-decision-page-programme-r3.md:674-688` · **medium** · spec-violation · confidence 0.99

**Evidence.** Under `Cheap checks ... Run them before executing`, item 6 says: `_REAL_PRODUCTS returns 6` even though the symbol was deleted.

**Failure scenario.** A worker runs the required pre-execution checks, finds no `_REAL_PRODUCTS`, and has no defined branch distinguishing “six products” from “the check is obsolete.” The worker can proceed with the stale 15-page denominator without the advertised falsifier ever deciding it.

**Suggested fix.** Replace the check with an explicit query of `clients WHERE is_real = 1` for the target database, or the named per-codebase oracle where that is the intended population.

### 5. Concurrent first boots can reapply the one-shot backfill

`db/schema.py:2894-2905` · **medium** · concurrency · confidence 0.98

**Evidence.** The block begins directly with `IF NOT EXISTS (...) THEN` and then performs the UPDATE and COMMENT, with no lock serializing concurrent first executions.

**Failure scenario.** During the first rolling deployment, task A and task B both enter the DO block before either marker is committed. A finishes and an operator then promotes `silver_canary` to 1, while B is paused between its guard and UPDATE. B resumes and writes the row back to 0 despite the marker now existing.

**Suggested fix.** Acquire a migration-specific `pg_advisory_xact_lock` before evaluating the guard, so a waiting task rechecks the marker after the first transaction commits.

### 6. Workbook provenance omits product-specific served slots

`scripts/page_status_workbook.py:15` · **low** · maintainability · confidence 1

**Evidence.** The new source table says `clients (is_real) x companies._SLOTS` defines the served population. The implementation calls `served_slots(code)`, which includes both `_SLOTS` and matching `_PRODUCT_SLOTS`.

**Failure scenario.** A maintainer reconstructing or refactoring the population from this source table uses only `_SLOTS` and silently drops ALM's product-specific Deal Ops slots from the workbook and sprint denominator.

**Suggested fix.** Change the source entry to `clients (is_real) x served_slots(code)`.

### 7. Migration rationale omits the actual update writer

`db/schema.py:2889-2890` · **low** · maintainability · confidence 1

**Evidence.** The comment says `api/services/vault/clients.py is the only production writer of this column`, but `api/services/control_plane/tenants.py::update_tenant` writes `changes["is_real"]` and is the operator path discussed immediately above.

**Failure scenario.** A future audit follows the claimed single writer and changes only vault/clients.py, overlooking the supported tenant-update path that can alter realness.

**Suggested fix.** Name both writers and narrow the relevant claim to neither writer issuing COMMENT statements.

### 8. Migration comment gives invalid tenant-update syntax

`db/schema.py:2872-2873` · **low** · api-contract · confidence 1

**Evidence.** The comment gives ``torque-admin tenant update <slug> --real``. The parser requires `tenant update --slug <slug> --real`; the slug is not positional.

**Failure scenario.** An operator copies the documented command while correcting a canary and argparse rejects the positional slug, leaving the row unchanged.

**Suggested fix.** Use `torque-admin tenant update --slug <slug> --real` here and in the matching test docstring.
