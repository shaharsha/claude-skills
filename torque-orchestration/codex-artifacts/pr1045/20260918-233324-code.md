## Findings

### 1. Advisory recheck is unsafe outside READ COMMITTED

`db/schema.py:2906-2914` · **medium** · concurrency · confidence 0.88

**Evidence.** `PERFORM pg_advisory_xact_lock(13551351); IF NOT EXISTS (...) THEN UPDATE ...; COMMENT ...;` assumes the post-lock query sees the first boot's commit, but the connection does not pin READ COMMITTED. PostgreSQL documents that fresh per-query snapshots expose new commits under READ COMMITTED, while REPEATABLE READ retains the transaction snapshot ([SPI snapshot behavior](https://www.postgresql.org/docs/17/spi-spi-execute.html)).

**Failure scenario.** If the database or `torque_app` has `default_transaction_isolation = 'repeatable read'`, two rollout tasks can establish snapshots before either commits. The second waits for the advisory lock but still sees its old snapshot afterward, concludes the comment is absent, and repeats the UPDATE. An operator promotion committed between the two migrations can therefore be reverted to 0.

**Suggested fix.** Explicitly establish READ COMMITTED on the init_db session before this DO block, or fail closed unless `current_setting('transaction_isolation')` is `read committed`. Add a concurrent repeatable-read control.

### 2. New test docstring shows invalid tenant-update syntax

`tests/test_canary_backfill.py:24-25` · **low** · correctness · confidence 1

**Evidence.** The text says `torque-admin tenant update <slug> --real`, while the parser requires `tenant update --slug SLUG`; line 192 of the same file uses the correct form.

**Failure scenario.** A reader copies the documented command and argparse rejects `<slug>` as an unexpected positional argument, so the intended operator promotion is not applied.

**Suggested fix.** Change it to `torque-admin tenant update --slug <slug> --real`.

### 3. Atomicity test passes when UPDATE and marker are split

`tests/test_canary_backfill.py:173-187` · **low** · test-gap · confidence 0.98

**Evidence.** After `init_db()`, the test only verifies both final effects: `assert _marker_exists(conn)` and that the three rows equal 0. It neither injects a failure between UPDATE and COMMENT nor verifies that both occupy one `_PG_MIGRATIONS` entry.

**Failure scenario.** A future edit splits UPDATE and COMMENT into separate tuple entries. Every test still passes on successful boots, but if COMMENT then fails, autocommit leaves the backfill committed without its marker; a later boot can rerun it and undo an operator promotion.

**Suggested fix.** Assert structurally that the guarded UPDATE and COMMENT are in one migration entry, or use a fault/role setup where COMMENT fails after UPDATE and verify neither effect commits. Also explicitly assert that a zero-row first boot creates the marker.
