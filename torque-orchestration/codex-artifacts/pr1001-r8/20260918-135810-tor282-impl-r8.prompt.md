## What the PR does

LR (a real client, product code `LR`) has no capture record, so its authored pages
cannot tell whether the last month present in the data was COMPLETE when the data
was taken. They therefore step the edge back one period and date to March where
April is complete.

This PR adds an `lr_meta` table (`db/schema.py`), writes one row from
`ingestion/lr_parser.py`, and lets `authored_pages/_recipe/as_of.py`'s
`capture_date` / `last_complete` use it. The capture constant is `2026-05-01`,
found in the source CSVs' own bytes and then authored as a literal.

Its 15 files (`git diff --name-only 4dad3ef2..HEAD`) include
`api/services/lr/data_qualification.py`, `authored_pages/_recipe/as_of.py`,
`authored_pages/{lr_forecast,lr_historical,lr_overview}/recipe.py`,
`db/schema.py`, `scripts/land_lr_capture_record.py` and four page READMEs.

Runtime context: `init_db()` runs unconditionally on every container boot.
`scripts/land_lr_capture_record.py --apply` writes to a live deployed database and
is run by a human operator; it is NOT run by this merge and NOT by CI.
